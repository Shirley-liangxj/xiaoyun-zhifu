# 小云智服 XiaoYun — 服饰电商 AI 售后客服协同工作台

> 面向中小服饰电商的 AI 售后客服系统：懂退换货政策、能溯源回答、低置信度自动转人工、知识缺口自动回流；并在 RAG 之上加了一层**由模型自主决策的工具调用控制层**（LLM function calling）+ 轨迹审计 + 高风险 HITL 确认。

## 项目背景

分析 8 份真实服饰电商客服对话后发现：中小店铺的平台机器人答非所问，人工回复慢且不专业，而服饰类目退换货率高达 20-30%，售后咨询量是其他类目的 3-5 倍。

## 核心功能

- **智能问答**：基于 RAG 的售后政策问答，支持多轮对话
- **来源溯源**：每个回答标注来自哪份政策文档
- **置信度评分**：低置信度回答自动标记，坐席确认后发送
- **知识缺口闭环**：无答案问题 → 转人工 + 记录缺口 → 运营补充标准答案 → 自动回流知识库 → 同类问题下次可被检索
- **控制层 Agent**：**模型自主工具调用**（LLM function calling）——把「查政策 / 查订单 / 退款试算 / 转人工」4 个工具的说明交给模型，由模型自己决定调哪个、是否追问、要不要转人工，代码不再写死 `if/elif` 分支；高风险动作（退款）由**代码级硬中断**强制转人工确认，模型无权执行；每轮写入 `backend/data/traces.jsonl` 可回放
- **知识库管理**：支持上传/管理售后政策、物流说明、FAQ；会话内可一键「写入知识库」
- **会话与工单**：对话历史、人工接管、工单流转
- **效果看板**：解决率、AI 采纳率、工单分布等核心指标（见下方「在线效果看板」）

## 技术栈

- **前端**：React + Vite + Tailwind CSS（设计系统：绿调 token 体系 + `.ds-*` 组件基类 + AI 协作硬约束）
- **后端**：Python FastAPI + SQLAlchemy；控制层在 `backend/app/agent/`
- **数据库**：SQLite（演示）；生产化规划 PostgreSQL + 多租户
- **AI**：智谱 GLM-4-Flash + FAISS 向量检索（RAG）
- **认证**：JWT

## 控制层说明（面试口径）

- **不是**生产级 Agent / 不接真实物流与支付；订单与退款规则为 **mock / 规则函数**，API 与 UI 均标注演示。
- **是**在现有 RAG + 阈值转人工之上加的一层**模型自主工具调用控制层**：把工具说明交给模型 → 模型返回 `tool_calls` → 代码执行并回灌结果 → 再问模型，最多 4 轮。
- **安全红线靠代码，不靠提示词**：① 系统里不存在「执行退款」的工具，模型物理上调不到；② 工具返回 `needs_human=True` 时代码**立刻中断循环**，不追加一轮问模型"你接下来想说什么"；③ 投诉/法律类高危词在**进 LLM 之前**由正则拦掉（0 次 LLM 调用）。
- **为什么砍掉原「意图分类」层**：原架构每轮固定 2 次 LLM（先分类、后生成），砍掉后简单咨询降到 1 次，高危场景 0 次——更安全、更省钱、更快。
- 轨迹文件：`backend/data/traces.jsonl`（本地运行生成，便于 badcase 回放：工具选错 / 该转没转 / 追问缺失）。
- 对外推荐说法：「控制层 / 工具编排 / 可审计」，避免夸大成「生产 Harness」。

## 设计系统（Design System）

为避免「vibe coding 每次改 UI 风格漂移」，本项目落地了一套可被 AI 调用的设计系统（方法论参考小红书「机器坏人 AI 版」《如何用 AI 维护一套设计系统》）：

- **品牌色系统化**：原有品牌绿 `#1D9E75` 扩展为 50–900 完整色阶，并定义 success / warning / danger / info 语义色，收敛原先散落的 blue/indigo/orange/green/red。
- **组件基类约束**：`src/index.css` 的 `@layer components` 定义 `.ds-card` / `.ds-btn-*` / `.ds-badge-*` / `.ds-input` / `.ds-stat-*` 等基类；页面只能复用，新增组件先扩展此处。
- **AI 协作硬约束**：`.cursorrules` 写死——颜色只能来自 token、布局只能复用 `.ds-*`、禁止硬编码与新增主色。让 AI 改界面从「随心所欲」变为「在约束下选择」。
- **反哺机制**：重复结构抽组件、好风格改 token 一处联动全站。

在线查看完整 Token 与组件真实渲染：**http://47.116.143.103:8080/design-system.html**

## 评测与质量保障

针对售后场景维护评测集（`eval/`）：早期 **17 题**黄金集验证 RAG 召回；后续扩展为 **67 题**分层集（easy 17 / normal 33 / hard 17，覆盖 8 类业务场景）。

### 消融对照（ablation）—— 证明 RAG 到底贡献了什么

只跑 RAG 一组数字，无法说明提升来自"资料库"还是"模型本来就强"。所以补了对照组：**同一份题、同一个模型、同一套判定标准**，唯一变量是"给不给资料"。

| 指标 | baseline（不给资料） | RAG（给资料） | 差值 |
|---|---|---|---|
| **人机分流判断准确率** | **0.00%**（0/11） | **90.91%**（10/11） | **+90.91pp** |
| 回答准确率（56 题） | 94.64% | 92.86% | −1.78pp |
| 整体准确率（67 题） | 79.10% | 92.54% | +13.44pp |
| 平均 tokens / 次 | 176.74 | 689.45 | +512.71 |
| P50 / P95 延迟 | 4831 / 9638 ms | 4832 / 8700 ms | — |

**结论**：**RAG 的价值不在"答得更准"**（常规售后问答上两者持平，题目偏常规、模型凭常识即可作答），而在**私域政策准确性与人机分流**——裸模型没有"该不该转人工"的概念，11 道超范围题全部照答。

**口径局限（如实声明）**：判定用关键词命中率代理指标，非人工评分；RAG 臂走传统检索链路、未走 Agent 全链路；embedding 检索成本未计入。完整报告见 [`eval/eval_report.md`](eval/eval_report.md)。

> 写作红线：**不得写"RAG 提升回答准确率"**（数据不支持）；旧数字「回答准确率 91.1%」为检索关键词覆盖率代理指标，已废弃（溯源见 PRD 12.3）。

**产品闭环：知识缺口自动回流**
问「卖不卖宠物狗粮」等低置信问题 → 转人工 + 记录知识缺口 → 会话内「写入知识库」或知识库页标记解决 → 索引后同类问题可被检索。证明「用户问倒 → 人工补知识 → 模型变聪明」。

> 测试集准确率 ≠ 线上解决率；面试请主动区分 Demo / 评测闸门 / 真实店铺数据。

## 数据来源与边界（诚实说明）

- 知识库基于**服饰电商售后领域公开语料 + 真实客服对话模式提炼**；含冲突/边界案例。
- 评测题为人工编写黄金集，不代表线上全量分布。
- 订单查询 / 退款试算为 **演示 mock**（`backend/app/data/orders_demo.json`），非真实业务系统。
- 演示客户「云裳服饰」为虚构示例。
