## 一、任务目标

不要继续美化作品集，也不要只改文案。先对整个项目做一次“作品集发布前的产品与工程审计”，找出所有属于**本来就应该在当前版本完成，却被错误留成未来规划**的问题，然后实际补齐 P0 项、运行验证，最后才能更新项目介绍。

这不是让你把项目做成生产级商业系统，而是要确保当前项目最核心的主张——“Agent 能根据任务选择工具，并在高风险场景安全转人工”——有完整功能、有正确指标、有评测证据、有一条真正跑通的任务链。

## 二、工作原则

1. 当前事实优先级：**源码与实际运行结果 > 当前评测题和输出 > README > 其他文档**。
2. 先运行 `git status`，保护用户已有的未提交改动；不要覆盖或回退无关修改。
3. 不要自动 `git commit`、`git push`、删除文件或部署。
4. 不要把现有 `docs/` 的结论直接当事实；文档只能帮助定位，最终以代码和实测为准。
5. 不得编造线上数据、商家效果、准确率或测试结果。
6. 不得把 mock 订单、退款试算说成真实订单查询或真实退款。
7. 不要只输出方案。必须在完成审计后，实际修改代码、补测试并验证。
8. 如果真实调用外部大模型会产生费用或使用用户 API Key，先说明调用数量、预计影响并征得用户同意；未经同意先完成可重复的离线测试与评测框架。
9. 每次修改前先说明：改哪些文件、改什么、为什么。
10. 如果审计发现本任务书没有列出的同类 P0 问题，也要纳入修复，不能只修示例。

## 四、已知 P0 改造一：Agent 全链路评测

### 当前问题

项目的差异点是 Agent 工具调用，但现有 `backend/app/services/eval_runner.py` 主要调用 `search_knowledge()`，测的是检索与阈值分流，没有真正评测：

- 模型是否选择正确工具；
- 工具参数是否正确；
- 缺少订单号时是否追问；
- 多个工具的调用顺序是否正确；
- 高风险问题是否被拦截；
- 人工接管是否完成；
- 一笔任务是否走到正确终态。

### 必须完成的改造

1. 保留现有 RAG 检索评测，但把误导性的“回答准确率”改成符合真实算法的名称，例如“检索关键词覆盖率”或“检索证据覆盖率”。
2. 新建独立的 Agent 评测集，建议路径：`eval/agent_cases.json`。
3. 新建 Agent 评测运行器，不要把逻辑继续塞进现有 RAG runner；建议独立为 `backend/app/services/agent_eval_runner.py`。
4. 评测集至少覆盖以下六类：
   - 工具选择；
   - 参数抽取；
   - 必要追问；
   - 高风险拦截；
   - 多工具顺序；
   - 人工接管与最终状态。
5. 每个用例至少包含：
   - 输入；
   - 预期工具序列；
   - 预期关键参数；
   - 是否应该追问；
   - 是否应该转人工；
   - 预期终态；
   - 风险等级；
   - 判定理由。
6. 不要只测 happy path，必须包含：
   - “发什么快递”应查政策，不能查订单；
   - “我的快递在哪”未给单号时必须追问；
   - 有订单号时正确提取；
   - 穿过、污损、退款金额场景必须进入人工流程；
   - 投诉、律师、曝光等高危场景应在调用模型前拦截；
   - 无关问题不能直接回答；
   - 大模型调用失败和超过最大轮数时必须转人工；
   - 未知工具或错误参数不能导致任务假成功。
7. 评测报告至少给出：
   - 工具选择准确率；
   - 参数准确率；
   - 必要追问正确率；
   - 高风险漏放数与漏放率；
   - 错误转人工数；
   - 完整任务成功率；
   - 每条失败用例的实际轨迹和错误原因。
8. 高风险漏放必须单独展示，不能被平均准确率掩盖。
9. 修改前端 `frontend/src/pages/Evaluation.jsx`，把 RAG 指标和 Agent 指标分成两个清晰区域，不混用同一“准确率”。
10. 增加对应 API、Schema 和测试。

### 评测必须分两层

#### A. 离线确定性测试（必须完成，不依赖真实模型）

通过 mock LLM/tool output 验证代码级规则：

- 高危命中时 LLM 调用次数为 0；
- `needs_human=True` 后模型循环立即停止；
- 系统不存在真实退款执行工具；
- 缺少订单号时不返回默认订单；
- 超过最大工具轮数转人工；
- LLM/embedding 异常转人工；
- 各状态写入正确。

#### B. 真实模型集成评测（需用户同意后运行）

使用当前模型实际验证工具选择与参数抽取。结果必须保存运行时间、模型、题集版本、配置和失败明细。没有用户同意，不得偷偷调用外部模型并生成假结果。

### 验收标准

- RAG 评测和 Agent 评测口径彻底分开；
- 测试能证明硬护栏不是提示词承诺；
- 每个 Agent 失败都有可复核轨迹；
- 前端不能再把检索覆盖率显示为真实回答准确率；
- 不得用历史 67 题结果冒充当前 Agent 评测结果。

## 五、已知 P0 改造二：结构化人工审核闭环

### 当前问题

当前退款流程本质上是：退款试算 → 买家确认 → 会话进入 `waiting_human`。它没有真正的坐席结构化审核动作，也没有批准、拒绝、补充材料等最终状态。`pending_confirmations.json` 还是本地 JSON 文件，存在并发、状态一致性和多实例问题。

### 必须完成的改造

1. 将 Pending Action 从 JSON 文件迁移到数据库模型，不再依赖 `backend/data/pending_confirmations.json` 作为正式状态源。
2. Pending Action 至少包含：
   - `company_id`；
   - `conversation_id`；
   - `action_type`；
   - 结构化 payload；
   - 风险原因；
   - 状态；
   - 创建时间；
   - 买家确认时间；
   - 坐席审核人；
   - 坐席审核时间；
   - 审核备注。
3. 明确状态机，例如：

```text
draft
  → buyer_confirmed
  → waiting_review
  → approved / rejected / need_more_info
```

4. 买家确认只代表“同意提交人工”，不能显示成“退款已确认执行”。
5. 坐席工作台增加结构化审核卡，至少展示：
   - 用户原话；
   - 订单/金额/天数；
   - 规则试算；
   - 风险原因；
   - 工具轨迹摘要；
   - 批准、拒绝、补充材料操作。
6. 当前仍然不得执行真实打款。坐席的“批准”只代表演示流程中的业务审核结果。
7. 所有状态变化必须有审计记录并校验租户权限。
8. 重复点击或重复请求必须幂等，不能产生多个审核单或重复变更状态。

### 验收标准

- 一笔灰度退款任务可以从买家请求走到坐席明确的终态；
- 页面不会把“提交人工”误写成“退款执行确认”；
- 刷新或重启服务后 Pending Action 不丢失；
- 非当前租户用户不能审核；
- 重复确认不会重复创建或重复审核；
- 有自动化测试覆盖主要状态和异常状态。

## 六、已知 P0 改造三：AI 建议采纳率口径修正

### 当前问题

`backend/app/routers/stats.py` 当前把所有 `role=ai_suggestion` 且 `is_sent=True` 的消息都计为“已采纳”。但买家端自动发送的 AI 回复也满足这个条件，因此所谓“AI 采纳率”混入了自动发送，不代表坐席真实采纳。

### 必须完成的改造

1. 不再用单个 `is_sent` 同时表达“是否发送”和“是否被坐席采纳”。
2. 根据现有数据结构选择最小可靠方案：扩展 Message 字段或新增 Suggestion/Decision 表。
3. 至少区分：
   - `auto_sent`：系统自动回复买家；
   - `accepted`：坐席原样采纳；
   - `edited_and_accepted`：坐席编辑后采纳；
   - `rejected`：坐席拒绝；
   - `pending`：等待坐席处理。
4. 修改所有相关写入路径：
   - 买家端自动回复；
   - 坐席采纳；
   - 编辑后发送；
   - 忽略/拒绝；
   - 重新生成建议。
5. 修改 Dashboard：
   - 自动发送量单独统计；
   - 坐席建议采纳率只以人工处理过的建议为分母；
   - 原样采纳与编辑采纳分开；
   - 明确公式和样本量。
6. 处理现有 SQLite 数据迁移，不能只改新表导致旧数据库启动失败。

### 验收标准

- 自动发送不再计入坐席采纳；
- 原样采纳、编辑采纳、拒绝和待处理可以分别统计；
- Dashboard 数字可由数据库记录逐条复算；
- API Schema、前端字段和数据库定义一致；
- 有测试覆盖四类状态。

## 七、已知 P0 改造四：知识缺口不能“假解决”

### 当前问题

`backend/app/routers/knowledge.py` 在解决知识缺口时调用 `index_document()`，但索引异常被吞掉，之后仍可能把缺口标记为 `resolved`。这会出现“页面显示已解决，实际没有进入索引”的假闭环。

### 必须完成的改造

1. 知识缺口只有在以下条件满足后才允许标记为 `resolved`：
   - 标准答案保存成功；
   - 知识文档创建成功；
   - 文档索引成功。
2. 索引失败时保留可重试状态，例如 `index_failed` 或 `pending_index`，同时返回明确错误。
3. 前端显示失败原因和“重新索引”操作，不能假装成功。
4. 每条已解决缺口应记录：
   - 对应知识文档 ID；
   - 来源会话/问题；
   - 解决时间；
   - 解决版本；
   - 可选的回归用例 ID。
5. 对完全相同问题至少继续聚合计数；再评估是否做文本归一化或语义聚类，不要在没有测试的情况下过度设计。
6. 增加测试：索引成功、索引失败、重试成功、重复解决、跨租户访问。

### 验收标准

- 索引失败时页面和数据库都不会显示已解决；
- 成功状态能够追溯到知识文档和版本；
- 可以重新索引并从失败状态恢复；
- 同类流程有自动化测试。

## 八、已知 P0 改造五：一条真正可验收的完整任务

### 当前问题

项目有很多页面和模块，但作品集需要证明同一笔任务确实能贯穿系统，而不是各页面分别存在。

### 必须完成的演示任务

同一个买家会话：

1. 买家提问标准政策问题；
2. Agent 调用政策检索；
3. 返回带来源的回答；
4. 买家继续提出包含金额、天数、穿着/污损条件的退款问题；
5. Agent 调用退款试算；
6. 代码因 `needs_human=True` 中断；
7. 买家确认提交人工；
8. 坐席看到结构化审核卡并接入；
9. 坐席选择批准、拒绝或补充材料；
10. 买家端看到对应结果；
11. 轨迹和审核记录可回放；
12. 若出现知识缺口，可以写入知识库并确认索引成功。

### 必须补的验证

- 后端集成测试覆盖主流程和至少三个异常分支；
- 前端实际点击一遍，确认按钮、状态和文案一致；
- API 响应、数据库状态、买家端和坐席端四者一致；
- 演示数据有明显标记；
- 不出现“已退款”“已打款”等虚假结果。
