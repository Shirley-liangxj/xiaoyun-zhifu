## 一、结论

**不能接受“P0 代码闭环已补齐”的结论，目前也不适合据此进入作品集最终改写。**

这轮改造不是完全无效：数据库持久化、买家自动回复与坐席建议的初步拆分、知识缺口索引失败不再直接标记 resolved、主评测页的 RAG 指标改名，这些方向是对的。但对照原任务书逐项验收后，实际状态更接近：

- 1 项主路径基本通过：RAG 主评测接口与页面的指标改名；
- 3 项只完成了局部：退款确认持久化、AI 建议状态拆分、知识缺口失败保留 pending；
- 2 项核心不通过：Agent 独立评测、一笔完整任务闭环；
- 另有 2 个新鲜实测出的逻辑问题：未知工具可被当作正常流程继续回答；确认单可以被错误关联到同租户的另一条会话。

所以这份 `项目补齐验收报告` 可以作为“开发进展记录”，不能作为“发布验收通过证明”。其中“7 场景 100%”“完整任务通过率 100%”“结构化人工审核闭环”“P0 已补齐”等表述需要撤回或降级。

## 三、关键问题与证据

### P0-1：所谓“Agent 7 场景评测”没有测 Agent

`backend/app/services/agent_eval_runner.py` 的工作方式是：

1. `_mock_plan()` 根据输入中的关键词，用另一套手写 if/regex 规则直接生成工具序列与参数；
2. 再把这套规则输出和 `eval/agent_cases.json` 中人工填写的预期答案比较；
3. 它没有调用 `run_agent_turn()`，没有 mock `llm_service.complete()` 驱动真实循环，也没有执行工具；
4. `need_human = high_risk or expected.need_human` 直接读取了预期答案，因此需要转人工的正例几乎不可能被测失败；
5. `end_to_end_success_rate` 只表示“手写计划与 fixture 相同”，并没有任何任务真正跑到终态。

因此“工具序列准确率 100%”“参数准确率 100%”“完整任务通过率 100%”都不能作为 Agent 能力证据。这不是普通的 mock 测试，而是测试对象被替换成了另一份规则答案。

题集本身也没有满足任务书：

- 每条用例缺少 `should_ask_followup`、预期终态、风险等级、判定理由；
- 没有“大模型失败”“最大轮次”“未知工具”“错误参数”“重复确认”等异常用例；
- “我的快递在哪、未给单号”这一必要追问场景缺失；
- `agent-007` 对“退款金额怎么算”反而预期直接调用 `calc_refund`，与“信息不足先追问”的要求冲突；
- 报告没有必要追问正确率、高危漏放率、失败轨迹或错误原因等任务书要求的指标。

更严重的是，真实 Agent 主循环确实存在 evaluator 没发现的问题。本次用内存数据库和两轮 mock LLM 实测：第一轮让模型调用不存在的 `unknown_tool`，第二轮返回“已经处理完成”。实际结果为：

```text
need_human=False
human_mode=False
intent=unknown_tool
unknown_tool 步骤状态虽然是 pending，但系统仍保存并返回正常完成答案
```

这违反了任务书中“未知工具或错误参数不能导致任务假成功”的硬要求。

另外，直接调用 `calc_refund("refund")`，在完全没有金额、天数和订单号的情况下，工具会自动补出：

```text
order_amount=199.0
days_since_purchase=5
refund_amount=199.0
order_id=DEMO-PENDING
```

这说明必要信息不足时仍可能生成一笔看似具体的退款试算，而不是先追问。页面即使标了“演示”，也不能把虚构参数当作用户任务输入。

### P0-2：数据库持久化完成了，但人工审核闭环没有完成

`human_review_actions` 表解决了“进程内 JSON 会丢”的问题，这是有效改进。但当前字段只有租户、会话、动作、标题、详情、payload、pending/confirmed 和时间；缺少任务书明确要求的：

- 风险原因；
- 买家确认时间；
- 坐席审核人；
- 坐席审核时间；
- 审核备注；
- approved / rejected / need_more_info 等最终状态。

当前 `confirm_pending_action()` 做的事情仍然只是：买家点击确认 → action 变 confirmed → 会话变 waiting_human。代码库中没有 HumanReviewAction 的坐席查询/审核 API，也没有坐席端的结构化审核卡和批准、拒绝、补材料按钮。因此报告所称“结构化人工审核”实际只是“结构化保存买家确认单”。

本次还实测出会话一致性问题：确认单属于会话 1，但请求里传入会话 2 时，系统会把确认单标为 confirmed，却把会话 2 改成 waiting_human，会话 1 仍保持 active：

```text
action_conversation=1
returned_conversation=2
c1_status=active
c2_status=waiting_human
action_status=confirmed
```

原因是代码使用 `conversation_id or item.conversation_id`，没有校验请求中的 conversation_id 必须等于审核单所属会话。至少应强制绑定审核单自己的 conversation_id，并对不匹配请求返回错误。

页面/模型中的 `action="refund_execute"`、标题“退款执行待确认”、步骤“待人工确认执行”也仍然比真实能力更强。实际只能“提交人工审核”，没有执行退款，更没有坐席批准后的模拟终态。

### P0-3：采纳状态拆了一半，核心公式仍不符合任务书

当前拆出了 `pending / accepted / rejected / auto_sent / legacy_sent`，并成功把买家自动回复排除出坐席采纳统计，这一部分成立。

但仍有三处未完成：

1. 接受接口允许坐席传入编辑后的 `body.content`，无论内容是否改变，都统一标成 `accepted`，没有 `edited_and_accepted`；
2. 采纳率公式是 `accepted / (pending + accepted + rejected)`，把尚未做决定的 pending 放进分母；任务书要求“只以人工处理过的建议为分母”，应至少是 `(accepted + edited_and_accepted) / (accepted + edited_and_accepted + rejected)`；
3. Dashboard 仍只展示“共生成多少、采纳多少、采纳率”，没有自动发送量、原样采纳、编辑采纳、拒绝、待处理的拆分和公式说明。

当前测试恰好把 `[pending, accepted, rejected]` 算成 33.3%，实际上把错误口径固化成了测试预期。测试通过不能证明业务指标正确。

### P0-4：知识缺口避免了“假 resolved”，但还不是可追溯闭环

正向改动成立：`resolve_gap()` 只有在 `index_document()` 成功后才写 resolved；失败返回 503 并保留 pending。

未完成项包括：

- `knowledge_gaps` 没有 knowledge_doc_id、resolved_at、解决版本、失败原因、回归用例 ID；
- 索引失败后只显示普通 pending，无法区分“尚未处理”和“处理过但索引失败”；
- 前端只有一次性 alert，没有在列表持续显示失败原因和针对该缺口的重试入口；
- 失败路径已经保存一篇未索引文档，再次点击解决会新建另一篇文档，存在重复文档风险；
- 自动化测试只测试 `resolution_outcome(True/False)` 这个纯函数，没有调用真实路由验证成功、失败、重试、重复解决和跨租户。

因此它解决了原 bug 的最窄部分，但没有达到任务书的完整验收线。

### P0-5：RAG 主链指标改名基本正确，但旧口径仍可能回流

`backend/app/services/eval_runner.py`、Schema 和 `frontend/src/pages/Evaluation.jsx` 已使用关键词覆盖口径，前端也明确写了“不等于生成答案正确”，这部分可以保留。

不过 `backend/scripts/eval_baseline.py` 仍把生成文本的关键词命中率称为 `answer_accuracy`，`eval/baseline_results*.json` 也保留同名字段。若这些脚本和文件继续被 README、作品集或面试材料引用，仍会产生“关键词命中=答案正确”的误导。应将活动脚本统一改名；历史结果如需保留，应显式标为历史口径并禁止作为当前结论。

### P0-6：没有完成任务书要求的一笔完整任务

现有最接近端到端的测试只覆盖：

```text
退款工具返回 needs_human
→ 创建 pending 审核单
→ 买家确认
→ 审核单 confirmed
→ 会话 waiting_human
```

缺少后半段：坐席看到结构化信息、选择批准/拒绝/补材料、买家看到最终结果、状态和审计记录一致。也没有实际浏览器走查证据或截图/录屏。报告中的 HTTP 检查只验证登录和 `/api/eval/agent` 返回自校验的 7 条结果，不能替代核心业务链路验收。

## 七、最终判断

这轮工作的价值是把几个明显的“口径和持久化坑”往前推了一步，但没有达到原任务书定义的交付标准。最不应该做的是拿当前 7/7 的自校验结果包装成 Agent 能力；最应该优先修的是：真实主循环离线测试、缺参追问/未知工具硬失败、坐席审核终态、采纳率公式，以及一条完整的页面任务链路。

在这些完成前，作品集可以写“我识别并开始修复这些问题”，不能写“项目已形成可验收的 Agent 协同闭环”。
