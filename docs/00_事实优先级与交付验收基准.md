# 小云智服｜事实优先级与交付验收基准

> 用途：这是小云项目的“单一事实入口”。后续作品集、录屏脚本、项目总结、简历项目描述和优化计划，都必须先对照本文件；不能再按上一轮聊天里刚出现的局部问题改一段就结束。
>
> 更新日期：2026-10-16

## 1. 先说结论

小云不是“一个能聊天的客服 Demo”，而是一个面向服装电商售后场景的 AI 客服协作工作台：

1. 对买家：用知识库回答有依据的售后问题，并给出来源/置信信号。
2. 对坐席：遇到低置信度、高风险或需要执行的事项，给出转人工建议和处理上下文。
3. 对产品/运营：把未命中、低置信度和转人工记录沉淀为知识缺口，进入评测集和知识库迭代。

本项目真正要证明的不是“模型会不会说话”，而是：**系统能不能在不同风险等级下做出合适的代理决策，并且让人知道它为什么这么做、出错后怎么接住。**

### 当前版本锁定

- 当前回归题库：**40 题**。
- 历史探索题库：**67 题**，只能称为历史实验/扩展题库；不能在同一段话里把 67 题说成线上当前题库。
- 当前项目有四类 Agent 工具：`search_policy`、`query_order`、`calc_refund`、`transfer_to_human`。
- `calc_refund` 当前只负责计算/给出建议，不执行真实退款；因此对外必须说“计算与建议”，不能说“自动退款”。
- 高风险命中、低置信度和需要执行的场景会进入人工协作；这是产品设计，不是系统失败。
- 当前系统价值闭环是：检索与引用 → 置信/风险判断 → 自动回答或人工接管 → 记录知识缺口 → 评测/知识迭代。
- 本地 Agent 控制层回归集：**12 条受控离线用例**，以 mock 外部 LLM 驱动真实 Agent 主循环；不得称为真实模型准确率。
- 本地退款审核状态：`pending_buyer → waiting_review → approved / rejected / need_more_info`；仅记录演示审核结果，不执行真实退款。
- 本地源码已完成 2026-10-16 P0 返工验收；**阿里云线上、GitHub 同步状态尚未验证/完成**，对外材料不得写成“线上已更新”。

### 指标口径修正（2026-10-22）

- 工作台有两个指标，**对外必须区分，不可混用**：
  - **AI 自动应答率** = 自动应答 ÷（自动应答 + 待人工处理）。这是商家真正关心的“AI 独立处理了多少”，做主指标。
  - **人工采纳率** =（原样采纳 + 编辑采纳）÷（原样采纳 + 编辑采纳 + 拒绝）。分母只算坐席已处理的建议。
- `auto_sent`（AI 直接回复买家）**不计入**人工采纳率分母：未经坐席审核，计入会把“自动应答量”混进“人工认可度”。
- **分母为 0 时一律显示「—」，不能显示 0%**。0/0 是无定义，渲染成 0% 会被误读成“AI 建议全被否”。这是已修复的真实 bug。
- 退款审核闭环（`HumanReviewAction`）与 AI 建议采纳（`Message.suggestion_status`）是**两条独立链路**：点了审核卡“批准”不会让采纳率变化，只有点「采纳发送/编辑后发送/忽略」才会。录制时要演出来必须两步都做。

### 评测链路修复（2026-10-22）

- **修复前**：RAG 评测必然返回「评测失败，请检查 API Key 和知识库索引」。真实原因不是 API Key 或索引问题，而是**前端 axios 默认 10 秒超时**，而后端 `eval_runner` 对 40 题逐题调用 `embed_text`，串行等 40 次外部 API。前端断开后**后端仍在空跑并继续消耗调用**。
- **修复后**：`eval_runner` 改为一次性 `embed_batch` 批量向量化（`rag.py` 拆出 `search_with_embedding`），前端评测接口单独放宽至 180s，错误文案区分超时/网络/后端返回。
- **实测：1.5 秒跑完 40 题**，检索命中率 100%、行为判断 40/40、误转 0、漏转 0。**现在可以放心在录屏中现场点「运行评测」。**
- 历史 `eval_report.md` 的 67 题数据仍是历史实验；当前 40 题的**行为判断与边界指标以线上实测为准**，但检索命中率 100% 属于检索层代理指标，不能等同于回答质量。

### 已知产品缺陷（不得隐藏）

- **能力边界对物流时效失效**：`intent_router` 的拦截规则要求「订单号 + 时效词」同时出现才触发，而客户首句通常不给订单号。实测问「快递什么时候能到」AI 会回“我帮您查询物流信息”——**承诺了做不到的事**。下一步应把关键词判定升级为意图级判定。

## 3. 对外叙事的唯一主线

以后录屏、作品集和面试介绍都围绕同一条任务链，不再打开多个页面各讲一遍功能：

> **同一个买家售后会话：先问一个有标准答案的问题 → 再提出一个涉及退款/高风险的灰度问题 → 系统展示检索、工具决策和人工接管 → 坐席处理 → 这次未命中沉淀为知识缺口 → 用回归集验证。**

这条主线同时证明：

- AI 为什么适合这个场景：知识多、规则常变、问题有风险分级；
- 为什么不是全自动：退款/投诉/曝光等高风险动作需要确认和人工兜底；
- Agent 的价值：不是多一个聊天框，而是根据任务选择检索、查询、计算或转人工；
- 产品经理的贡献：定义代理边界、工具契约、评测口径、知识闭环和上线取舍。

## 4. 所有交付物的验收标准

### 4.1 录屏/视频

交付前必须同时满足：

- [ ] 开场 15 秒内说清：给谁、解决什么、为什么用 AI。
- [ ] 全片只有一个核心角色（买家）和一个完整任务链，不用功能清单串场。
- [ ] 每个点击/输入都能在配音里被解释：正在做什么、系统为什么这样做、给谁带来什么价值。
- [ ] 至少展示一次“自动回答”和一次“不能自动做、转人工”的对比。
- [ ] 至少展示一次来源/置信度/工具调用/转人工理由中的两类证据。
- [ ] 说清实际技术与产品机制：RAG、Agent 工具调用、风险前置拦截、人工接管、评测集；每个技术后面必须跟业务作用。
- [ ] 结尾给出 2 个有验收口径的下一步，不写“继续优化体验”这种空话。
- [ ] 实际录屏路径与脚本逐步对齐；必须先跑通一次再写最终配音稿。

### 4.2 飞书作品集

- [ ] 首屏是定位、目标用户、核心任务和 Demo/视频入口，不先放长篇自我感想。
- [ ] 结构为：问题与场景 → 目标与取舍 → 端到端方案 → 关键机制/PRD → Demo/视频 → 评测证据 → 风险与兜底 → 结果与局限 → 下一步。
- [ ] PRD 只放能证明产品判断的部分：用户故事、流程、状态/异常、工具契约、验收标准；不堆模板截图。
- [ ] 当前 40 题与历史 67 题分栏标识，注明用途和日期。
- [ ] 每个指标都写口径、样本、日期和局限；没有真实业务数据就明确写“离线评测/演示数据”。
- [ ] “我的贡献”写决策和产出，不把 AI 生成的代码全部算成个人工作。
- [ ] “下一步”必须写成：问题 → 动作 → 指标/验收线 → 预期决策。

### 4.3 项目总结/简历

- [ ] 一句话能说清“面向谁、解决什么任务、用什么 AI 机制、带来什么结果”。
- [ ] 技术名词只保留能解释产品取舍的：RAG 解决知识更新/可引用，Agent 负责工具决策，HITL 负责高风险兜底。
- [ ] 不夸大为真实商业上线、真实 GMV 或真实客服降本；演示部署、离线评测、历史实验分开写。
- [ ] 结果至少给一个可核验的评测口径；若没有线上数据，写清“当前不能证明什么”。

## 5. 一票否决项

出现以下任一项，交付不能标记为完成：

1. 用历史 67 题冒充当前线上 40 题。
2. 把“计算退款/生成建议”说成“自动执行退款”。
3. 只列技术栈，不解释技术选择和风险边界。
4. 只说发现了问题，不给出动作、验收标准和决策点。
5. 脚本、实际页面和配音三者无法逐步对应。
6. 用“效果很好/体验更好/持续优化”代替数据和可验证动作。
