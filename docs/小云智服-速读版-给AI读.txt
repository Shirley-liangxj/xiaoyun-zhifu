一、项目速览

目标客群：日单量 50–500、客服 1–3 人的中小服饰卖家（用不起智齿/七鱼年费几万，又被平台免费机器人折磨）

二、定位与边界
----------------------------------------
定位三次收敛：v1「AI 替代人工」→ v2.1「AI 赋能人工的协同工作台」→ v2.3 现行「高置信自主答 / 低置信转人工 / 转人工后发送权在坐席」。
雷区：不能说"所有回答都要人工确认后才发出"——那只描述转人工后的坐席协同，不是买家主路径，会被追问"那你跟纯人工客服差在哪"。

做：服饰售后问答（退换货/物流/质量/退款/尺码/政策）· 低置信拒答 + 进人工队列 · Agent 工具调用 · 会话轨迹回溯 · 来源溯源 · 置信度评分 · 知识库管理 · 坐席工作台 · 工单流转 · 效果看板 · 多租户雏形 · 评测闸门
不做：完全无人值守 · 售前导购/营销 · 售中订单修改 · 电话呼叫中心/全渠道 · 非服饰行业通用客服 · 私有部署定制

北极星：AI 自主解决率 FCR，目标 ≥ 65%（MVP 假设值，非实测）。FCR 口径写死三条件：① AI 给出有效回答（非拒答/非转人工/非仅安抚）② 回答后 30 分钟内未就同一问题追问 ③ 48 小时内未升级为差评/纠纷。
明确不采用的"口径游戏"：静默即解决（买家不回 ≠ 解决）· 转人工前掐断 · 非活跃时段注水。


三、市场与竞品（结论级）
----------------------------------------
三层竞品：① 第三方厂商（晓多/乐言/网易七鱼/智齿/美洽）——谁在跟我抢客户 ② 平台官方 AI 客服（阿里店小蜜/京东京小智/抖音飞鸽）——谁在用免费教育市场 ③ 技术路线参照（Dify/FastGPT/MaxKB）——我的选型是不是行业共识

核心发现：市场不是空白，是"被绑定式服务"。
- 第三方全部瞄准中大型：最便宜的美洽 3–8 万/年（10 席位）；网易七鱼 10–25 万/年；智齿 30–50 万/年起。客单价逻辑决定它们不会往下做。
- 平台官方全部免费，但生态绑定：店小蜜日均 UV<50 免费、超出 0.2 元/通，仅服务淘系；京小智 5.0 新商免费 1 年、成熟约 8000 元/年，仅服务京东；飞鸽基础版免费，仅服务抖音电商。四条共同特征：生态绑定 / 营销导向（重心售前，售后是附带）/ 黑盒不可溯源 / 立场偏商家。
- 一手实测 5 家店结论：体验差距的根源不是 AI 能力，是订单数据打通能力（天猫超市选订单后秒退款、催发货直转人工；中小店铺仍是菜单式、答非所问）。

差异化四支柱：定位（只做售后不做全栈）· 信任（答案可溯源、指标可审计、立场中立、零编造）· 能力（亲手跑通全链路 + 当前 40 题回归 + Agent 控制层离线评测；历史 67 题消融作归因证据）· 生态（跨平台 + 可自托管，数据归商家）


四、需求与一手证据
----------------------------------------
痛点三重叠加：机器人答非所问（拼多多某店问"怎么退货"→ 回欢迎语；说"转人工"→ 回"没有订单"）· 人工回复不专业（淘宝某店回"怎么了呢"）· 响应慢（先连发 3 条欢迎语，几十秒后才给答案）

一手证据现状：assets/evidence/ 有 11 张截图，覆盖 5 家店铺（拼多多/淘宝/天猫超市），含答非所问类（小懒猫美衣23号店、米比旗舰店、Dearday）、平台自营对照（天猫超市 6 张）、转人工失效（减少家的店90：菜单无退货、连错 3 次转人工失败）。另有小红书服饰售后话题抓取原始件。
口径待统一：01 文档写"8 份真实客服对话"，实物是"5 家店铺 11 张截图" → 对外统一说"5 家店铺、11 张一手截图"。
一处待确认：02 文档写"诚少家的店90"，截图文件名是"减少家的店90"。

技术选型：为什么是 RAG —— 纯规则（僵硬、维护成本高，配"退换货"要穷举几十个同义词）否决；纯大模型直答（会编造店铺政策、不可溯源、售后答错要商家赔钱）否决；RAG 锚定商家自己的政策文档，可更新、可溯源、低成本。

已知技术债（主动说）：company_id 在 URL 上不是密钥，是演示级隔离 · PII 未做脱敏中间件/留存清理/加密列（原则已写、工程未做完）· human_review_actions 目前无过期机制/锁 · Agent 主循环对 query_order 命中的 confidence 保留展示值 0.7 与工具真实返回不同源 · run_tool 存在 duplicate kwarg 潜在坑


六、评测体系 + 消融对照（本项目最值钱的部分）
----------------------------------------
产物：当前 `eval/questions.json`（40 题正式回归集）+ 历史 `eval/baseline_results.json`（67 题 × 2 臂）+ `eval/eval_report.md` + `backend/scripts/eval_baseline.py`

历史 67 题消融集分层（当前正式回归集为 40 题）：
- category：退换货 10 / 物流 10 / 质量 10 / 支付 10 / 通用 10 / 超出范围 11 / 尺码 3 / 售后政策 3
- difficulty：easy 17 / normal 33 / hard 17（用于分析难例，不作发版硬门槛）
- expected_behavior：answer 56 / transfer_human 11（核心标签：该答还是该转）

阈值 0.6 是校准出来的：置信度公式 = 无检索 0.25；有结果 0.4 + avg(top-3 score) × 0.55，截断 0.1–0.95。校准原则：用 67 题在候选阈值上扫一遍；优化目标不是"回答准确率最高"，而是"转人工判断"——宁可略增误转，也要压漏转（客诉风险）。选定后写入 company_settings.confidence_threshold 默认值。面试说法："0.6 是评测闸门上的工作点，不是行业标准常数。"

口径修订（为什么废弃"回答准确率 91.1%"）：旧口径实为在 56 道 answer 题上统计检索返回的资料片段是否包含 expected_keywords（覆盖率 ≥50%），全程未调用 LLM 生成任何回答（验算 51/56 = 91.07% ≈ 91.1%）。它是检索代理指标，回答的是"资料搜到了没"，不是"AI 答得对不对"。新口径：判定模型生成的回答文本；并新增 baseline 臂（不给资料直接问模型）做消融对照，使 RAG 的贡献可归因。

消融对照主结果（67 题 × 2 臂）：
- 人机分流判断准确率：baseline 0.00%（0/11）→ RAG 90.91%（10/11），+90.91pp
- 回答准确率（56 题）：94.64%（53/56）→ 92.86%（52/56），−1.78pp
- 整体准确率（67 题）：79.10% → 92.54%，+13.44pp
- 平均总 tokens/次：176.74 → 689.45
- P50 / P95 延迟：4831 / 9638 ms → 4832 / 8700 ms
- 实际 LLM 调用次数：66 → 56（−10）
- 千次对话成本（按 glm-4-air ¥0.5/百万 tokens 假设单价折算）：¥0.0884 → ¥0.3447

三条结论：
1. RAG 的价值不在"答得更准"——常规售后问答 94.64% vs 92.86% 未显著提升；更狠的证据是 normal 桶（29 道最典型常规题）RAG 的 answer 反而少 3 题（29/29 → 26/29），把资料原文直接塞进 prompt 对常规问题可能产生干扰。这是"检索结果怎么用"的优化空间，不是"检索有没有用"。
2. RAG 不可替代的是私域政策准确性与人机分流——裸模型根本没有"该不该转人工"这个概念，11 道超范围题（写代码/天气/股票/翻译…）全部照答（0%）；RAG 靠"检索不到 → 置信度 <0.6 → 强制转人工"接住 10 道。
3. 分流本身就省成本——RAG 实际 LLM 调用 56 次 < 裸模型 66 次，每拦下一次无效生成就省一次 token。
最关键读法：+13.44pp 的整体提升 100% 来自 transfer 那 11 题（+10 题），answer 题上总量是 −1 题。所以"RAG 提升整体准确率"必须靠转人工来支撑，不能归因给回答质量。

另一个宝藏发现（关键词口径会奖励幻觉）：id=13 尺码题问"面料是什么"——裸模型编了个"棉质面料"→ 命中关键词判对；RAG 如实说没资料转人工 → 判错。一个"诚实说不"的回答在关键词口径下得分低于一个"编答案"的回答。这证明了评测指标本身会激励幻觉，也是推翻旧口径、改判定对象 + 补 baseline 臂的直接动因。价值：同时体现指标设计的批判性、主动做归因实验的意识、敢推翻自己已发布数字的诚实度。

必须如实声明的局限（追问时不可改口）：① 判定用关键词命中率代理指标，不是人工评分，有假阴假阳 ② RAG 臂走的是传统检索链路（search_knowledge + 阈值），未走新的 Agent 全链路 → 本次测的是"知识库的价值"，不含 Agent 工具调用能力 ③ embedding 检索成本未计入，真实成本高于表中值 ④ 1 条样本因 SSL 瞬时断连失败未重跑，记入 failed_count ⑤ 样本量 67，分位数仅供方法演示，不构成生产级性能承诺 ⑥ 成本栏是假设单价折算，实际生成侧花 ¥0（GLM-4-Flash 免费额度）

简历可用 / 不可用：
- 历史归因证据：「人机分流转人工判断准确率：裸模型 0% → RAG 90.9%（历史 67 题消融对照）」
- 当前不沿用旧整体准确率数字；发布口径以 40 题回归 + Agent 控制层离线评测为准
- 加分：「RAG 对常规问答提升不显著，其价值在私域政策准确性与人机分流」
- 不能写：「RAG 让回答准确率从 X 提升到 Y」（数据不支持，实测略降）
- 不能写：「回答准确率 91.1%」（旧口径，已废弃）


七、Agent 控制层重构（从意图硬路由到模型自主工具调用）
----------------------------------------
改造前的三个问题：① 每轮固定消耗 2 次 LLM（先分类、再生成），成本与延迟翻倍 ② 决定权在代码不在模型，每加一个新能力就要多写一个分支 ③ 实测稳定性问题：traces.jsonl 里同一句"发什么快递"，会话 16 判为 query、会话 17 判为 consult，同一输入两次判定不同，根因是分类环节有两套逻辑打架（LLM 判定 vs 关键词覆盖）。

新架构：① 会话已在 waiting_human → 走人工建议分支（不进循环）② 高危正则前置拦截 detect_high_risk()（投诉/辱骂/律师/起诉/曝光/报警/工商/消协/315）→ 直接转人工，llm_calls=0 ③ function calling 主循环 MAX_TOOL_ROUNDS=4：调 llm.complete(messages, tools=list_tool_schemas())；无 tool_calls → 用 content 作终答；有 tool_calls → run_tool 后结果回灌；若结果 needs_human → 代码硬中断立刻进人工分支，不再追加一轮 LLM（模型无权继续）。

四个工具（tool_registry.py）：
- search_policy：查店铺政策/规则（包装 RAG + 置信度），参数 query（必填），needs_human 随置信度（<0.6 时 true）
- query_order：查订单状态与物流（mock），参数 order_id（选填），needs_human 恒 false
- calc_refund：退款试算（纯规则），参数 order_id/amount/days_since_purchase（选填），needs_human 恒 true
- transfer_to_human：转人工，参数 reason（必填），needs_human 恒 true

三条安全红线（靠代码，不靠提示词）：① 系统里不存在"执行退款"的工具，模型物理上调不到会打款的函数，只能试算 ② 工具返回 needs_human=True → 代码立刻中断循环，不追加一轮问模型"你接下来想说什么" ③ 投诉/辱骂/法律类高危词在进 LLM 之前用正则拦掉。原则：提示词约束可以被模型绕过，代码判断不会。

五个关键设计决策：① 废弃 LLM 意图分类只保留高危正则（简单咨询 2 次 → 1 次 LLM，高危 0 次）② 正则范围有意收窄，只拦投诉/法律/曝光类，把"穿过/污损"摘出去交给 calc_refund，否则"穿过沾了粉底液能退吗"会在进模型前被拦死，退款试算 + HITL 确认卡这条演示路径永远不会被触发 ③ query_order 的隐藏兜底改为显式开关 fallback_to_first（默认关），原实现用户没给单号时偷偷返回第一条订单，会教模型学成永远不传 order_id ④ 出参契约不变，intent / plan_steps 保留 key（前端"执行计划卡"依赖），语义调整为"模型实际调了哪些工具" ⑤ 知识缺口回流重新挂钩到 search_policy 分支内（原来埋在会被替换掉的 _run_consult() 里会丢失）。

实测记录（模型不调工具 ≠ 不会调工具）：只在系统提示写"超范围请礼貌说明你只能处理售后"→ 模型用嘴拒绝了（回"建议您使用专门的编程社区"）但没调工具；把"是否属于售后范畴"提为最高优先级前置判断 + 明确写"禁止只用文字说我帮不了您来代替调用工具" + 删掉"能直接回答就直接回答"的放行口子 → 正确调用 transfer_to_human。结论：模型不调工具不是不会调，是它没觉得有必要调，它愿意用嘴拒绝、不愿意用手办事；GLM-4-Flash 这类轻量模型指令遵循较弱，规则冲突时会挑宽松那条执行。

验收（直连 run_agent_turn 脚本，全部通过）：写 Python 排序代码 → 转人工 ✓｜今天北京天气 → 转人工 ✓｜"你好" → 直接回答（反向测试防误伤）✓｜快递三天没动静 → 调 query_order 并追问单号（不返回他人订单）✓｜DEMO-1002 这单什么时候到 → 调 query_order 自己抽单号 ✓｜衣服穿过沾粉底液 199 元第 5 天能退吗 → calc_refund 试算 → 硬中断 → 待人工确认（不自动打款）✓｜支持花呗分期免息吗 → 检索到但置信度 <0.6 → 强制转人工 ✓

会话轨迹字段：ts / conversation_id / company_id / input / intent（含 source）/ tools（名称+参数+返回摘要）/ llm_calls / needs_human / pending_confirmation_id / interrupt_reason / grounded / output。价值：Agent 自己决策就必须能回放出错时它为什么这么判断。

已知局限：human_review_actions 目前无过期/锁策略 · 真实外部 LLM 工具选择准确率尚未做授权后的批量评测（当前已补确定性 Agent 控制层回归，不冒充真实模型指标）· duplicate kwarg 潜在坑。

九、8 个高频追问的速答
----------------------------------------
Q1 你的项目跟别的 AI 客服作品集有什么不一样？
A：大部分是"上传 PDF → 问答"的 RAG 套壳。我的不同：① 8 家竞品拆解发现"跨平台中立售后"这个结构性空白，不是为做 RAG 而做 RAG ② 定义了完整指标并写死口径（防行业口径游戏）③ 5 家店铺 11 张一手实测 + 67 题分层评测 + 消融对照，不是纸面设计。

Q2 RAG 到底给你的产品带来了什么？（核心题）
A：做了消融对照才敢回答——RAG 的价值不在"答得更准"（常规问答 94.6% vs 92.9%，无显著提升，normal 桶甚至掉 3 题，说明塞原文反而干扰）。它不可替代的是人机分流：该转人工的判断从裸模型 0% 提到 90.9%，裸模型压根没有"该不该转人工"这个概念，11 道超范围题它全答了。据此把优化重点放在分流准确率和超范围问题的可控处理上，而不是盲目堆检索。

Q3 你的评测本身可靠吗？（追问陷阱，答好加分最多）
A：不可靠，我标了四条局限：关键词命中率代理指标不是人工评分；RAG 臂走传统检索链路、没走新的 Agent 全链路；embedding 成本没计入；67 题样本偏小。而且我发现这套指标会奖励幻觉——问"面料是什么"，裸模型编"棉质面料"判对，我的系统如实说没资料转人工反而判错，越诚实得分越低，所以我才推翻旧口径、把判定对象换成真实生成的回答，并补 baseline 臂做归因。

Q4 Agent 跟 ChatGPT 有什么区别？怎么保证它不乱来？
A：区别在它动手不只是动嘴——不把分支写死在代码里，而是把「查政策/查订单/退款试算/转人工」四个工具的说明书交给模型，让它自己决定调哪个、要不要追问、要不要转人工；加新能力只需补工具说明，不动主流程。但安全判断不交给模型：① 系统里根本不存在"执行退款"的工具，它物理上调不到会打款的函数，只能试算 ② 工具一旦返回"需要人工"，代码立刻中断循环 ③ 投诉/法律类高危词在进模型之前被正则拦掉，0 次 LLM 调用。一句话：决策可以交给模型，红线必须留在代码里。我实测过——只在提示词里写"超范围请礼貌说明"，模型会用嘴拒绝但不调工具，必须堵掉"用嘴拒绝"这条退路。

Q5 为什么把原来的意图分类架构推翻了？
A：三个原因：① 原来每轮固定 2 次 LLM，成本和延迟翻倍 ② 决定权在代码不在模型，每加一个能力就要多写一个分支 ③ 实测出稳定性问题：traces.jsonl 里同一句"发什么快递"，两次会话一次判查订单、一次判查政策，同一输入两个结果，根因是分类环节两套逻辑打架。所以把决定权交回模型，代码只留执行和安全。

Q6 0.6 这个阈值怎么定的？
A：不是拍的，是用 67 题在候选阈值上扫出来的。优化目标不是"回答准确率最高"，而是"转人工判断"——宁可略增误转，也要压住漏转，因为漏转在售后就是客诉风险。定完写进配置默认值。不过我从不把它当行业常数讲，它只是我这套评测集上的一个工作点。

Q7 店小蜜都免费了，你这项目是不是伪需求？
A：免费的代价是绑死生态 + 不中立 + 数据不归你。三家平台全部只服务自家，没有一家跨平台，而多平台开店是中小商家常态——这个空白巨头不会填，帮竞品平台做客服等于自杀，这是结构性约束不是能力问题。另外它的重心在售前转化（会主动劝买家不退货），售后是附带，客诉场景买家不信任。所以它们的免费战恰好验证了市场价值，也恰好把"跨平台、中立、可溯源"空了出来。

Q8 这个项目上线了吗？有多少商家在用？
A：没有，这是个人作品集 Demo，没有服务过真实付费商家，这点在 README 里写得很明确。所有评测数字都是 67 题评测集（合成 golden set）口径，不等于线上解决率，真实 query 分布要上线后回流，这是我知道的"数据飞轮"下一步。技术成熟度上：多租户、PII、反幻觉设计原则都写了，但工程上还是演示级——company_id 在 URL 上不是密钥、没有脱敏中间件、没有留存清理。我知道差距在哪，也知道补的顺序。
