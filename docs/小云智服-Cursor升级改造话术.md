## 一、项目现状（整段复制给 Cursor，Ctrl+L 或 Ctrl+I）

```
项目：小云智服，面向服装电商的 AI 售后客服（个人作品集项目）。
技术栈：后端 FastAPI + SQLAlchemy + SQLite；前端 React + Vite + Tailwind；
AI：智谱 GLM-4-Flash（免费）做生成，FAISS 做向量检索。

当前已有能力（不要动）：
- RAG 检索 + 生成：用户问售后问题 → 检索知识库 → 大模型生成回答
- 置信度阈值判断：低于阈值自动转人工
- 知识缺口回流：无答案问题沉淀进知识库，形成自迭代闭环
- 67 题分层评测集（在 eval/ 目录下，用于量化回答质量）

当前缺失（这是要升级的方向）：
- 没有意图路由：用户消息直接进 RAG，不做意图分类
- 没有工具调用：查订单 / 算退款这类"办事"能力为空，系统纯问答
- 没有会话轨迹记录：每轮 input → model → tool → output 不可回放
- 没有 HITL 确认交互：高风险动作没有"待人工确认"的环节

升级目标：在现有 RAG 底座上【加一层控制层】，让系统从"只会答"变成"能分步办且每步可解释"。不推翻现有检索/生成逻辑。

约束：
- 不要新增核心依赖（复用现有 GLM 接口、现有向量库）
- mock 数据要标注清楚是"演示数据"，不能假装真实业务系统
- 保持现有对话接口可用，新增模块以追加为主
```

## 二、升级目标（4 个里程碑，让 Cursor 自己设计实现）

- **M1 意图路由**：用户消息先分类（咨询类 / 查询类 / 操作类 / 转人工），再分流处理。
- **M2 工具注册表 + 2 个能跑的工具**：查订单（用 mock 假订单数据）、算退款（纯规则函数，退款需人工确认绝不自动执行）。
- **M3 会话轨迹审计**：每轮对话记 input → 意图决策 → 调用的工具与返回 → 最终输出，可回放（建议 jsonl 格式，接你 67 题 badcase 复盘）。
- **M4 统一入口**：把 M1–M3 串成一次对话循环，给用户"执行计划卡"而非纯文本；高风险步骤标红"待人工确认"。

## 三、跟 Cursor 对齐颗粒度（你确认时问它这些）

不要上来就让它写，先对齐范围，避免它大改你现有逻辑：

1. **它打算新增哪些文件、改哪些文件？**（对齐范围——应是新增 agent/ 包，不动现有 RAG）
2. **意图分类用什么做？**（应复用现有 GLM 接口做 zero-shot，不新增模型/不新增依赖）
3. **mock 数据准备放哪、怎么标注"演示数据"？**（面试你要能说清这是 mock）
4. **轨迹记录存哪、什么格式？**（建议 `backend/data/traces.jsonl`，接你 67 题复盘）
5. **验收标准怎么定？** M1 用这三条测：
   - "我的快递三天没动静" → 应判「查询类」
   - "这衣服穿过沾了粉底液能退吗" → 应判「转人工」
   - "七天无理由怎么退" → 应判「咨询类」
   对 ≥4/5 条即通过。

## 四、边界红线（也给 Cursor 看，避免它跑偏）

- ❌ 不硬塞 DeepSeek Harness 框架（它是思路不是依赖；且 v0.1 预览版不稳，会导致 Demo 跑不起来）。
- ❌ 不编真实物流/订单系统（工具一律用 mock，面试如实说）。
- ✅ 你的护城河（67 题 / 0.6 阈值 / 转人工 97%）升级时强化，不丢。
