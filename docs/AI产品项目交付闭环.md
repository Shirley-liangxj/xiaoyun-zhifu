# 小云智服｜AI 产品项目“证据到交付”闭环

> 目的：修正过去“资料研究得很好，但下一轮只修局部文字；知道缺点，却没有把缺点转成方案和验收”的问题。

## 1. 以后每轮只允许走这条链

```text
事实盘点 → 冲突分级 → 研究结论 → 项目映射 → 交付设计 → 实际执行 → 独立核验 → 结论/下一步
```

任何外部资料都必须填写“项目映射卡”，否则只能算参考资料，不能进入作品集或脚本。

## 2. 项目映射卡（研究结论不能直接跳到文案）

| 字段 | 必填内容 |
|---|---|
| 外部结论 | 资料原话的可复述结论，区分事实与作者建议 |
| 对小云的对应场景 | 买家问答、退款灰度、坐席接管、知识缺口、评测中的哪一个 |
| 当前证据 | 源码位置、页面、命令输出、评测结果或明确写“暂无证据” |
| 产品判断 | 这个结论是否改变功能、交互、指标或叙事；为什么 |
| 具体动作 | 改哪个文档/页面/脚本/题库；动作必须能执行 |
| 验收标准 | 什么结果出现，才算动作有效 |
| 未解决限制 | 当前不能证明什么、为什么不能证明 |

## 3. 从 AI-PM 面试指南提炼出的项目规则

### 3.1 先讲任务，不先讲模型

所有介绍先回答：给谁、在什么任务里、痛点是什么、为什么现在需要 AI。技术放在“为什么这样做”的后面。

应用到小云：先讲服装电商售后坐席在规则多、知识更新快、风险等级不同的情况下，如何在一个会话里完成回答或转人工；再解释 RAG/Agent/HITL 各自承担什么责任。

### 3.2 先验证能力，再决定方案

不因为“可以用大模型”就加功能。每个新增能力先回答：模型是否能稳定完成？检索是否有证据？工具是否有安全边界？失败时回到谁？

应用到小云：退款执行、物流实时查询、自动承诺等需求，先做小样本验证；没有真实接口和授权时，只展示建议或只读结果，不把动作伪装成已实现。

### 3.3 评测与兜底是默认配置

评测集从需求开始就存在，不等上线后再补。当前先把 40 题当作现行回归集；新增能力另建带版本号的小型金丝雀集，不再靠“总题数越多越好”。

应用到小云：补一组 Agent 轨迹题，至少覆盖“该不该调用工具、调用哪个工具、何时追问、何时转人工”；每题同时验答案质量和代理决策。

### 3.4 用数据逐级赚取代理权

小云当前适合“高控制、低代理”的 v1：标准售后问答可自动答；退款/投诉/曝光/不确定问题给建议并人工接管；不执行真实资金动作。

只有当特定风险类型在回归集和人工抽检中达到预先约定的阈值，才讨论扩大自动化范围。没有阈值的“放开自动化”一律不进入路线图。

### 3.5 下一步必须可决策

以后不再写“继续优化效果”。每个下一步按以下句式：

> 因为【证据/问题】，在【范围】做【动作】，以【指标与验收线】判断；若达标则【下一决策】，否则【回退/换方案】。

小云示例：

1. 因为当前 40 题只能证明静态题库表现，补 20 条 Agent 轨迹题，分别验工具选择/追问/转人工；若三类通过率都达到约定阈值，再评估扩大自动回答范围，否则保留人工接管。
2. 因为历史文档仍有 67 题口径，建立“当前/历史”字段并在作品集和 README 统一引用；验收是所有对外页面不再出现无标签的 67 题当前表述。
3. 因为低置信度记录还没有形成可追踪闭环，给知识缺口增加“来源、处理状态、回归题 ID、上线版本”；验收是每条已处理缺口都能在下一次回归中定位结果。

## 4. 每种交付物如何落地

### 4.1 录屏脚本

先写“任务状态表”再写配音：

| 镜头 | 页面/操作 | 系统证据 | 配音要回答的问题 |
|---|---|---|---|
| 开场 | 项目首页/标题卡 | 定位和用户 | 谁在什么任务里获益 |
| 标准问题 | 买家端输入政策问题 | 引用/置信信号 | 为什么可以自动答 |
| 灰度问题 | 同一会话输入退款/投诉 | Agent/风险拦截 | 为什么不能直接执行 |
| 协作 | 坐席接管 | 上下文、建议、状态 | 人工接手如何更快更安全 |
| 闭环 | 知识缺口/评测页 | 题库/指标 | 这次失败如何变成下一版能力 |
| 收束 | 结果卡 | 当前边界与下一步 | 项目现在能证明什么、还不能证明什么 |

配音稿必须从这张表生成；任何配音句子找不到对应画面或证据，删掉或补画面。

### 4.2 作品集

作品集不是 PRD 文件堆，而是“决策证据链”。最少保留：

1. 一页定位和任务；
2. 一张端到端流程/状态图；
3. 一段关键 PRD（工具契约、风险规则、验收标准）；
4. 一个可点击 Demo/视频；
5. 一张当前评测表和历史实验边界；
6. 一段失败/兜底与知识闭环；
7. 一段带指标的下一步。

### 4.3 项目总结/面试回答

统一采用：定位 → 核心任务 → 机制 → 证据 → 取舍 → 局限 → 下一步。每一段至少有一个“因为……所以……”的产品判断和一个证据。

## 5. 我以后必须执行的自检

在给出“已完成/最终版/可以投递”之前，必须回答并记录：

- 我依据的当前事实是什么？是否和历史资料混用？
- 用户要的最终交付物具体是什么？是否满足完整验收清单？
- 每个外部洞察落在哪个项目动作上？
- 我实际运行/打开/核对了什么？证据在哪里？
- 还有哪些不能证明？是否诚实写出？
- 下一步是否有动作、指标、阈值和决策，而不是口号？

如果其中任一项没有答案，只能报告“进行中/有缺口”，不能说“最终版”。

## 6. 对本次反馈的直接修正

问题不在于用户的提示词不够专业，而在于我此前把“研究、项目审计、脚本改写、事实校验”当成四个孤立任务，缺少一份跨轮次的事实基线和交付验收契约。以后以本文件和 `00_事实优先级与交付验收基准.md` 为上游，不再只修用户刚指出的一句话。
