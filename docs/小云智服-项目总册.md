### 技术栈（硬事实，改动前先核对）

| 层 | 实际用的 |
|---|---|
| 前端 | React + Vite + Tailwind（品牌绿 `#1D9E75` 完整色阶 + `.ds-*` 组件基类 + `.cursorrules` 硬约束） |
| 后端 | Python **FastAPI** + SQLAlchemy；控制层在 `backend/app/agent/` |
| 数据库 | SQLite（演示态）；向量：**FAISS**，按 `company_id` 分索引 `company_{id}.index` |
| 模型 | **智谱 GLM-4-Flash**（生成，官方免费额度）+ `embedding-3`（2048 维，独立付费通道） |
| 认证 | JWT |

> ⚠️ **口径纠错（必背）**：这套栈**不是 Dify，也不是 FastGPT**。`FastAPI` 是 Python Web 框架，`FAISS` 是向量检索库——都跟"FastGPT"只差字面。
> 正解类比：**"Dify/FastGPT 是毛坯房装修套餐，我是自己打地基、自己砌墙"**——因为电商售后场景要控切分策略、阈值逻辑、转人工规则，通用框架里这些要改源码才能动。

## 模块一：产品定位（M1，2026-08 上旬）

> **我的职责**：主导。产出 `docs/00_产品定位.md`（现 v2.4）

### 1.1 定位的三次收敛

| 版本 | 定位 | 为什么改 |
|---|---|---|
| v1 | AI 替代人工（无人客服） | 起手式，行业通稿写法 |
| v2.1 | **AI 赋能人工的协同工作台** | 意识到"全程无人"在售后场景不成立——答错要商家赔钱 |
| v2.3（现行） | **高置信 AI 自主答 / 低置信转人工 / 转人工后发送权在坐席** | 对齐真实代码。旧表述"AI 只做建议、每条都要人点发送"**只描述了转人工后的坐席协同**，不是买家主路径 |

> 这一条是**面试高频雷区**：如果按旧文档说"所有回答都要人工确认后才发出"，会被追问"那你跟纯人工客服差在哪"。

### 1.2 产品边界（写死，不扩）

**做**：服饰售后问答（退换货/物流/质量/退款/尺码/政策）· 低置信拒答 + 进人工队列 · Agent 工具调用（工作台四工具）· 会话轨迹回溯 · 来源溯源 · 置信度评分 · 知识库管理 · 坐席工作台 · 工单流转 · 效果看板 · 多租户雏形 · 评测闸门

**不做**：完全无人值守 · 售前导购/推荐/营销 · 售中订单修改（改地址/改尺码/取消） · 电话呼叫中心/全渠道 · 非服饰行业通用客服 · 私有部署定制（MVP 阶段）

### 1.3 核心价值主张

> AI 不是来抢客服饭碗的：80% 标准问题由 AI 直接答买家（省等待）；20% 没把握的进人工队列，坐席带着 AI 建议处理。

量化目标（MVP 假设值，非实测）：FCR ≥ 65% · 人工转接率 ≤ 25% · 平均响应 < 3 秒 · CSAT ≥ 85%

## 模块二：需求分析与用户研究（M1–M2）

> **我的职责**：主导。产出 `docs/01_需求分析与用户研究.md`（现 v2.3）

### 2.1 痛点诊断（三重叠加）

| 痛点 | 一手证据 | 影响 |
|---|---|---|
| **机器人答非所问** | 拼多多某店：买家问"怎么退货"→ 机器人回"亲亲 欢迎光临 小店 有什么能为您效劳的呢~"；说"转人工"→ 回"没有订单" | 用户 frustration，直接流失/差评 |
| **人工回复不专业** | 淘宝某店：人工回"怎么了呢"，不直接回答退货怎么办 | 多轮沟通，单次咨询 > 5 分钟 |
| **响应慢** | 某旗舰店：先连发 3 条欢迎语，几十秒后才给答案 | 等待期流失 |

### 2.2 一手证据现状（**已从"缺失"补成"有实体"**）

`assets/evidence/` 现有 **11 张截图，覆盖 5 家店铺**（拼多多 / 淘宝 / 天猫超市），含：

- 答非所问类：小懒猫美衣23号店、米比旗舰店（连发 4 条欢迎语）、Dearday（答非所问）
- 平台自营对照：天猫超市 6 张（智能客服入口 → 逼选商品 → 未选订单卡住 → 选订单后秒退款 → 催发货直转人工 → 人工接入）
- 转人工失效：减少家的店90（菜单无退货、连错 3 次转人工失败）

外加小红书服饰售后问题抓取原始件：`xhs_fushi_raw.json` / `xhs_chima_raw.json` + 两份快照 txt + `docs/小红书实测-服饰售后问题分类-20260920.html`。

> ⚠️ **口径待统一**：`01` 文档写"8 份真实客服对话"，实际归档是"**5 家店铺 11 张截图**"。建议对外统一说**"5 家店铺、11 张一手截图"**（可数、可出示）。

### 2.3 KPI 体系与"防口径游戏"

- **北极星**：AI 自主解决率（FCR），目标 ≥ 65%
- **FCR 口径写死**（三条件同时满足才计入）：① AI 给出有效回答（非拒答/非转人工/非仅安抚）② 回答后 30 分钟内未就同一问题追问 ③ 48 小时内未升级为差评/纠纷
- **明确不采用的口径游戏**：静默即解决（买家不回 ≠ 解决）· 转人工前掐断（转人工必须真实接通）· 非活跃时段注水

> 面试话术价值：竞品普遍存在"报表解决率 ≠ 真实解决率"（有的把买家问完不回话算解决）。把口径写死并支持**下钻到原始对话复核**，本身就是产品差异化。

### 2.4 为什么是 RAG，不是微调 / 不是纯规则

| 方案 | 否决理由 |
|---|---|
| 纯规则机器人 | 僵硬、维护成本高、识别不了自然语言变体（配置"退换货"要穷举"缩水/变小/走样"几十个同义词） |
| 纯大模型直答 | 会编造店铺政策（幻觉）、不可溯源、**售后答错要商家赔钱** |
| **RAG** ✅ | 锚定商家自己的政策文档：可更新（改文档几分钟生效 vs 微调几天）、可溯源、低成本 |

## 模块三：竞品分析与差异化（M2）

> **我的职责**：主导。产出 `docs/02_竞品分析与差异化定位.md`（现 v2.1）
> **数据来源**：8 家厂商公开信息 + 5 家店铺一手实测 + 2026 年第三方横评

### 3.1 三层竞品选择逻辑（每层回答一个不同问题）

| 层级 | 代表 | 回答什么问题 |
|---|---|---|
| 第三方厂商 | 晓多、乐言、网易七鱼、智齿、美洽 | 谁在跟我抢客户（市场分层） |
| 平台官方 AI 客服 | 阿里店小蜜、京东京小智、抖音飞鸽 | 谁在用免费策略教育市场（生态威胁） |
| 技术路线参照 | Dify、FastGPT、MaxKB | 我的技术选型是不是行业共识 |

### 3.2 核心发现：市场不是空白，是"被绑定式服务"

**第三方厂商全部瞄准中大型**——最便宜的**美洽 3–8 万/年（10 席位）**，对 1–3 人小店仍"买不起"；网易七鱼 10–25 万/年、智齿 30–50 万/年起。**客单价逻辑决定了它们不会往下做。**

**平台官方全部免费，但绑死生态、且是营销导向**：

| 平台 | 产品 | 收费 | 核心限制 |
|---|---|---|---|
| 淘宝/天猫 | AI 店小蜜 | 日均 UV<50 免费，**0.2 元/通** | 仅服务淘系 |
| 京东 | 京小智 5.0 | 新商免费 1 年，成熟约 8000 元/年 | 仅服务京东 |
| 抖音 | 飞鸽智能客服 | 基础版免费 | 仅服务抖音电商 |

四条共同特征：**① 生态绑定 ② 营销导向（重心售前转化，售后是附带）③ 黑盒不可溯源 ④ 立场偏向商家（店小蜜会主动劝买家不退货）**

> **"店小蜜免费了，你还有市场？"** —— 被问最多的问题。三层答法：
> ① 巨头免费是**生态战争不是公益**（把商家更牢绑在自家平台，数据沉淀即资产）
> ② 三家全部生态绑定、**没有一家跨平台**，而多平台开店是中小商家常态——这个结构性空白巨头谁也不会填（**帮竞品平台做客服等于自杀**）
> ③ 数据自主是平台方案永远给不了的

### 3.3 差异化四支柱

| 支柱 | 内容 |
|---|---|
| **定位** | 只做售后，不做全栈。竞品卖"客服+CRM+营销+工单"全家桶，我只解决"自动答 + 答不了转人工"——功能少 = 便宜 + 一天上手 + 售后更专注 |
| **信任** | 答案可溯源（引用知识库原文出处）· 指标可审计（FCR 口径写死 + 可下钻）· 立场中立 · 零编造（超纲直接拒答转人工） |
| **能力** | 亲手跑通全链路 + 当前 40 题回归 + Agent 控制层离线评测；历史 67 题保留作消融归因（有测试证据，不是纸面设计） |
| **生态** | 跨平台 + 可自托管，知识库与对话数据归商家 |

### 3.4 一手实测结论（5 家店铺）

**体验差距的根源不是 AI 能力，是订单数据打通能力**——天猫超市这类平台级店铺已打通订单系统（选订单后秒退款、催发货直转人工），体验好；普通中小店铺仍是菜单式、答非所问。**而这恰恰是小微商家买不起的。**

## 模块五：技术实现（M3–M3 尾）

> **我的职责**：定义 + 验收；实现由 AI 编码工具按 PRD 完成，我逐条验收行为与口径

### 5.1 后端：10 个已注册 Router

`auth` · `users` · `conversations` · `tickets` · `knowledge` · `stats` · `eval` · `settings` · `public_chat`（买家端，含控制层） · `quick_replies`

### 5.2 已落地能力（超出基础 MVP 的）

| 能力 | 说明 |
|---|---|
| **双端真打通** | 买家 RAG 问答 ↔ 坐席待人工列表 ↔ AI 建议采纳，两端数据真联通（多数 Demo 是空壳） |
| **分层兜底** | 阈值 0.6 + 拒答话术 + 转人工出口 |
| **知识缺口闭环** | 低置信自动记录缺口 → 运营补标准答案 → 会话内一键"写入知识库"并索引 → 同类问题下次可被检索。**证明"用户问倒 → 人工补知识 → 模型变聪明"** |
| **多租户雏形** | JWT 带 `company_id`；公开 API `?company_id=`；**FAISS 按公司分索引，检索不跨公司** |
| **容错/冷启动** | 未配 Key 或 API 挂 → 不静默编造，走拒答 + 转人工；空库自动 seed + `reset-demo` 一键灌演示数据 |
| **会话轨迹** | `backend/data/traces.jsonl`，每轮落一条 JSON，可回放 badcase |

### 5.3 降级设计（面试常问"挂了怎么办"）

| 场景 | 代码行为 |
|---|---|
| 未配 `LLM_API_KEY` | `ValueError` → 走拒答话术 + 转人工；坐席建议卡写"未配置" |
| HTTP 失败/超时（LLM 60s、embedding 30s） | `ExternalServiceError` → 拒答 + `waiting_human` |
| 响应 JSON 畸形 | 同上 |
| 高危关键词 | 纯正则，不依赖 LLM，**不存在失败场景** |
| 工具调用失败 | 失败信息回灌给模型，由模型决定追问或转人工 |
| RAG/embedding 失败 | 检索当空 → 低置信 → 转人工 + 记缺口 |
| 限流 | 无独立 429 重试队列，表现为 HTTP 失败 → 同一套降级 |

> 原则一句话：**宁可不答、转人工，也不编政策。**

### 5.4 已知技术债（主动说，比分被追问强）

1. `company_id` 出现在 URL 上，**不是密钥**——演示级隔离，不是零信任 SaaS；无行级加密、无独立库
2. PII：字段最小化、默认不拿对话微调模型；**未做**脱敏中间件、留存到期清理、加密列（"设计原则已写、工程未做完"）
3. `human_review_actions`：当前有结构化状态，但尚未补过期机制与并发锁
4. Agent 主循环对 `query_order` 命中的 `confidence` 保留展示值 0.7，与工具真实返回不同源
5. `run_tool(name, message, company_id=..., fallback_to_first=False, **args)` 存在 duplicate kwarg 潜在坑（当前 schema 未暴露这两字段）

## 模块六：评测体系与口径修订 🏆（M5，2026-09-21）

> **这是整个项目最有分量的一段**，也是最稀缺的作品集证据。当前产物：`eval/questions.json`（40 题正式回归）+ Agent 控制层离线评测；`eval/baseline_results.json`（历史 67 题 × 2 臂）+ `eval/eval_report.md` 保留作归因。

### 6.1 评测集演进：17 题 → 历史 67 题 → 当前 40 题回归集

> 17 题和 67 题是历史演进材料；当前源码发布口径以 `eval/questions.json` 的 40 题服饰售后回归集为准。

| 维度 | 构成 | 用途 |
|---|---|---|
| `category` | 退换货 10 / 物流 10 / 质量 10 / 支付 10 / 通用 10 / **超出范围 11** / 尺码 3 / 售后政策 3 | 看哪类场景误转、漏转 |
| `difficulty` | easy 17 / normal 33 / hard 17 | 分析难例，不作发版硬门槛 |
| `expected_behavior` | **answer 56 / transfer_human 11** | **核心标签：该答还是该转** |
| `expected_keywords` | 关键词列表 | golden 的可判定部分（**不是**标准答案范文） |

### 6.2 阈值 0.6 是校准出来的，不是拍的

置信度公式（`ai_suggestion._calc_confidence`）：**无检索 → 0.25；有结果 → `0.4 + avg(top-3 score) × 0.55`**，截断在 0.1–0.95。

校准原则：
1. 用 67 题在候选阈值上扫一遍
2. **优化目标不是"回答准确率最高"，而是"转人工判断"——宁可略增误转，也要压漏转（客诉风险）**
3. 选定 0.6 写入 `company_settings.confidence_threshold` 默认值

> 面试说法：**"0.6 是评测闸门上的工作点，不是行业标准常数。"**
> （历史对比：0.4 低于当时最低有效分，安全网几乎不触发）

### 6.3 ⚠️ 口径修订：为什么废弃「回答准确率 91.1%」

**旧口径的真实含义**：在 56 道 answer 题上，统计**检索返回的资料片段**是否包含 `expected_keywords`（覆盖率 ≥ 50%）——**全程未调用 LLM 生成任何回答**。验算：`51 / 56 = 91.07% ≈ 91.1%` ✓

→ 它是**检索代理指标**，回答的是"资料搜到了没"，**不是**"AI 答得对不对"。

**新口径**：判定**模型生成的回答文本**是否命中关键词；并新增 **baseline 臂**（不给资料、直接问模型）做消融对照，使"RAG 到底贡献了什么"**可归因**。

### 6.4 消融对照主结果（67 题 × 2 臂）

| 指标 | baseline（不给资料） | RAG（给资料） | 差值 |
|---|---|---|---|
| **人机分流判断准确率** | **0.00%**（0/11） | **90.91%**（10/11） | **+90.91pp** |
| 回答准确率（56 题） | 94.64%（53/56） | 92.86%（52/56） | −1.78pp |
| **整体准确率（67 题）** | **79.10%** | **92.54%** | **+13.44pp** |
| 平均总 tokens / 次 | 176.74 | 689.45 | +512.71 |
| P50 / P95 延迟 | 4831 / 9638 ms | 4832 / 8700 ms | — |
| 实际 LLM 调用次数 | 66 | 56 | **−10** |
| 千次对话成本（假设单价折算） | ¥0.0884 | ¥0.3447 | +¥0.2563 |

**三条结论（面试口径）**

1. **RAG 的价值不在"答得更准"**——常规售后问答 94.64% vs 92.86%，**未显著提升**（题目偏常规，模型凭常识即可作答）。更狠的证据：`normal` 桶（29 道最典型的常规题）RAG 的 answer 反而**少 3 题（29/29 → 26/29）**——把资料原文直接塞进 prompt 对常规问题**可能产生干扰**。这是"检索结果怎么用"的优化空间，**不是"检索有没有用"**。
2. **RAG 不可替代的是私域政策准确性与人机分流**——裸模型根本没有"该不该转人工"这个概念，**11 道超范围题（写代码/天气/股票/翻译…）全部照答**（0%）；RAG 版靠"检索不到 → 置信度 < 0.6 → 强制转人工"接住 10 道。
3. **分流本身就省成本**——RAG 版实际 LLM 调用 56 次 < 裸模型 66 次。每拦下一次无效生成就省一次 token。

**最关键的读法**：+13.44pp 的整体提升，**100% 来自 transfer 那 11 题（+10 题）**；answer 题上总量是 −1 题。所以**"RAG 提升整体准确率"这个说法必须靠转人工来支撑，不能归因给回答质量**。

### 6.5 另一个宝藏发现：关键词口径会奖励幻觉

评测中有这么一题（`id=13`，尺码类，问"面料是什么"）：

- **裸模型**：编了一个"棉质面料"→ 命中关键词 → **判对**
- **RAG**：知识库里没有 → 如实转人工 → **判错**

**一个"诚实说不"的回答，在关键词口径下得分低于一个"编答案"的回答。** 这直接证明了**评测指标本身会激励幻觉**，也是我推翻旧口径、改用真实生成回答判定 + 补 baseline 臂的直接动因。

> 这条是**面试含金量最高的一段**：它同时体现了 ① 指标设计的批判性 ② 主动做归因实验的意识 ③ 敢推翻自己已发布数字的诚实度。

### 6.6 必须如实声明的局限（**追问时不可改口**）

1. 判定用**关键词命中率代理指标**，不是人工评分 → 有假阴/假阳
2. **RAG 臂走的是传统检索链路**（`search_knowledge` + 阈值），**未走新的 Agent 全链路** → 本次测的是"知识库的价值"，**不含** Agent 工具调用能力
3. **embedding 检索成本未计入**（`embedding-3` 是独立付费通道，每次提问至少 1 次调用）→ 真实成本高于表中值
4. 1 条样本因 SSL 瞬时断连失败未重跑（记入 `failed_count`）
5. 样本量 67，分位数仅供方法演示，**不构成生产级性能承诺**
6. 成本栏是**假设单价折算**（按 glm-4-air ¥0.5/百万 tokens），实际生成侧花 ¥0（GLM-4-Flash 免费额度）

### 6.7 简历可用表述

- ✅ **历史归因证据**：「人机分流转人工判断准确率：裸模型 0% → RAG 90.9%（历史 67 题消融对照）」
- ✅ 当前可写：「40 题正式回归集 + 7 场景 Agent 控制层离线评测；不把 mock 结果写成真实大模型准确率」
- ✅ 加分写法：主动说明"RAG 对常规问答提升不显著，其价值在私域政策准确性与人机分流"
- ❌ **不能写**："RAG 让回答准确率从 X 提升到 Y"（数据不支持，实测略降）
- ❌ **不能写**："回答准确率 91.1%"（旧口径，已废弃）

## 模块七：Agent 控制层重构 🏆（M5，2026-09-21）

> **从「意图硬路由」到「模型自主工具调用」**。这是对 2026 年 JD 最有说服力的一段。产物：`backend/app/agent/`

### 7.1 为什么要改（改造前的三个问题）

改造前流程：`分类意图（调 1 次 GLM 做 4 分类）→ 代码 if/elif 挑分支`

| # | 问题 | 证据 |
|---|---|---|
| 1 | **每轮固定消耗 2 次 LLM**（先分类、再生成），成本与延迟翻倍 | — |
| 2 | **决定权在代码不在模型**。模型明明能理解语言，却被限制成"只能输出一个分类标签"；**每加一个新能力就要多写一个分支** | — |
| 3 | **实测出稳定性问题** | `traces.jsonl` 里同一句"发什么快递"，会话 16 判为 `query`（去查了订单）、会话 17 判为 `consult`（正确回答了政策）——**同一输入两次判定不同**。根因：分类环节有两套逻辑打架（LLM 判定 vs 关键词覆盖，`source` 字段暴露） |

**改造目标**：把"该做什么"的决定权从代码交给模型；代码只负责**执行模型选的工具**与**卡死安全红线**。不推翻现有 RAG 检索/生成逻辑。

### 7.2 新架构执行流程

```
买家消息
  ├─ ① 会话已在 waiting_human → 走人工建议分支（不进循环）
  ├─ ② 高危正则前置拦截 detect_high_risk()
  │     命中 投诉/辱骂/律师/起诉/曝光/报警/工商/消协/315
  │     → 直接转人工，llm_calls = 0
  └─ ③ function calling 主循环（MAX_TOOL_ROUNDS = 4）
        messages = [system(工具使用规则) + user]
        loop:
          resp = llm.complete(messages, tools = list_tool_schemas())
          无 tool_calls → 用 resp.content 作终答，break
          有 tool_calls → run_tool(...) → 结果回灌 messages
             └─ 若 结果.needs_human → 代码硬中断，立刻进人工分支，
                不再追加一轮 LLM（模型无权继续）
```

### 7.3 四个工具（`tool_registry.py`）

| 工具 | 用途 | 参数（JSON Schema） | `needs_human` |
|---|---|---|---|
| `search_policy` | 查店铺政策/规则（包装 RAG + 置信度） | `query`（必填） | 随置信度，< 0.6 时为 true |
| `query_order` | 查订单状态与物流（mock） | `order_id`（选填） | 恒 false |
| `calc_refund` | 退款试算（纯规则） | `order_id`/`amount`/`days_since_purchase`（选填） | **恒 true** |
| `transfer_to_human` | 转人工 | `reason`（必填） | **恒 true** |

### 7.4 🛡️ 安全红线：靠代码，不靠提示词（**本次改造最重要的原则**）

| # | 约束 | 实现位置 |
|---|---|---|
| 1 | **系统里不存在"执行退款"的工具**——模型物理上调不到会打款的函数，只能"试算" | `tools/refund_calc.py` 只做规则计算，无写操作 |
| 2 | 工具返回 `needs_human=True` → **代码立刻中断循环**，不追加一轮去问模型"你接下来想说什么" | `agent_loop.py` 主循环 |
| 3 | 投诉/辱骂/法律类高危词在**进 LLM 之前**用正则拦掉 | `intent_router.detect_high_risk()` |

> 为什么不能靠提示词？**提示词约束可以被模型绕过，代码判断不会**（见 7.6 实测）。

### 7.5 五个关键设计决策

1. **废弃 LLM 意图分类，只保留高危正则**——简单咨询从 **2 次 → 1 次** LLM；高危场景 **0 次**（更安全：情绪激动的客户不该让 AI 接；更省钱；更快）
2. **正则范围有意收窄**——**只拦投诉/法律/曝光类，把"穿过/污损"摘出去**交给 `calc_refund` 判断。否则"穿过沾了粉底液能退吗"会在进模型前被拦死，**退款试算 + HITL 确认卡这条演示路径永远不会被触发**
3. **`query_order` 的隐藏兜底改为显式开关**——原实现用户没给单号时 `found = orders[0]` **偷偷返回第一条订单**，演示效果好但与"模型自主决策"冲突（模型会学成永远不传 `order_id`）。改为 `fallback_to_first` 参数（默认关），未命中时返回 `need_order_id=True`，由模型主动追问
4. **出参契约不变**——`intent` / `plan_steps` 保留 key（前端"执行计划卡"依赖），仅语义调整为"模型实际调了哪些工具"，如 `direct_answer` / `query_order+calc_refund`
5. **知识缺口回流重新挂钩**——原 `record_knowledge_gap()` 埋在被循环替换掉的 `_run_consult()` 里会丢失，现改挂在 `search_policy` 分支内，自迭代闭环保持完整

### 7.6 实测记录：模型不调工具 ≠ 不会调工具

| 改动 | 结果 |
|---|---|
| 只在系统提示里写"超范围问题请礼貌说明你只能处理售后" | ❌ 模型**用嘴拒绝了**（回"建议您使用专门的编程社区"），但 `need_human=False`——**它没调工具** |
| 把"是否属于售后范畴"提为**最高优先级前置判断** + 明确写"**禁止只用文字说我帮不了您来代替调用工具**" + 删掉原规则里"能直接回答就直接回答"的放行口子 | ✅ 正确调用 `transfer_to_human` |

> **结论**：模型不调工具，不是"不会调"，而是"**它没觉得有必要调**"——它愿意用嘴拒绝，不愿意用手办事。所以提示词必须堵掉"用嘴拒绝"这条退路。**GLM-4-Flash 这类轻量模型指令遵循较弱，规则冲突时会挑宽松那条执行**（原第 6 条就是模型的逃跑借口）。

**验收（直连 `run_agent_turn` 脚本）**：

| 输入 | 期望 | 结果 |
|---|---|---|
| 帮我写一段 Python 排序算法代码 | 转人工 | ✅ |
| 今天北京天气怎么样？ | 转人工 | ✅ |
| 你好 | 直接回答（**反向测试防误伤**） | ✅ `direct_answer` / `need_human=False` |
| 我的快递三天没动静 | 调 `query_order` 并**追问单号** | ✅（不返回他人订单） |
| DEMO-1002 这单什么时候到 | 调 `query_order` 并**自己抽单号** | ✅ |
| 这衣服穿过沾了粉底液，199 元，第 5 天能退吗 | `calc_refund` 试算 → **硬中断** → 待人工确认 | ✅（不自动打款） |
| 你们支持花呗分期免息吗 | 检索到但置信度 < 0.6 → **强制转人工** | ✅ |

### 7.7 会话轨迹（可审计性）

`backend/data/traces.jsonl` 每轮落一条 JSON：`ts` / `conversation_id` / `company_id` / `input` / `intent`（含 `source`）/ `tools`（名称+参数+返回摘要）/ `llm_calls` / `needs_human` / `pending_confirmation_id` / `interrupt_reason` / `grounded` / `output`

> **价值**：Agent 会自己决策，出错就必须能回放"它当时为什么这么判断"。这也是 badcase 复盘与面试演示的核心材料。

### 7.8 已知局限（主动说）

1. **真实外部 LLM 工具选择准确率尚未做授权后的批量评测**，当前已补确定性 Agent 控制层回归，不冒充真实模型指标
2. `human_review_actions` 尚未补过期机制与并发锁
3. 历史 67 题只覆盖"该答/该转"；当前另有 7 场景控制层评测覆盖工具序列、参数与高危分叉
4. 若模型在 args 里传入与 `run_tool` 签名同名参数会触发 duplicate kwarg（当前 schema 未暴露，属潜在坑）

## 模块八：踩过的坑（现象 → 后果 → 规避办法）

### 8.1 产品 / 需求坑

**坑 1：把"无人客服"当默认定位**
- **现象**：v1 定位写"AI 替代人工"，链路里没有人工出口
- **后果**：与售后场景的本质冲突——答错要商家赔钱，"全程无人"直接把风险全兜在 AI 身上
- **规避**：把"低置信必须兜底、高风险动作不自动执行"作为**产品边界的第一条**写进定位，而不是当作附录里的异常处理

**坑 2：用"AI 只出建议、人工点发送"描述买家主路径**
- **现象**：`00_产品定位.md` 早期版本把坐席侧协同写成了主链路
- **后果**：访客会觉得这产品跟纯人工没差别；自己讲的时候也会前后矛盾
- **规避**：**以代码为准回头审文档**——买家高置信路径是 AI 自主答，坐席建议卡只存在于转人工之后。`docs/功能全景-给协作方.md` 就是为纠正这类漂移而建的对照表

### 8.2 评测 / 指标坑（本项目最值钱的坑）

**坑 1：用"资料搜到了没"冒充"AI 答得对不对"**
- **现象**：早期评测在 56 道题上只统计**检索片段**是否含关键词，不调用 LLM 生成回答，得出"回答准确率 91.1%"
- **后果**：这个数字被写进 PRD、简历、交接文档，**看起来像个能打的成绩，实际是检索覆盖率**。一旦面试官问"你的判定标准是什么"，当场就会崩
- **规避**：① 判定对象改成**生成的回答文本**；② 补 **baseline 臂**做归因（不给资料直接问模型）；③ 主动在报告里写"口径局限"；④ 把旧数字明确标为"已废弃"。**已经发出去的数字，自己有责任推翻它**

**坑 2：指标会奖励幻觉，而且是自己设计出来的**
- **现象**：`id=13` 面料题——裸模型**编了**"棉质面料"→ 命中关键词判**对**；RAG **如实说"没有资料"**转人工 → 判**错**
- **后果**：这套指标下，**越诚实得分越低**。如果没发现，优化方向会被指标带偏成"让模型更敢说"
- **规避**：发现这个反例后，把它写进报告当作**指标失效的证据**，并据此推动口径修订。**评测指标本身也需要被评测**

**坑 3：合并口径、跨版本比数字**
- **现象**：`97% 转人工判断`、`91.1% 回答准确率`、`100% 检索命中`、`误转 1.8% / 漏转 9.1%` 这几个数被反复混用在不同文档里
- **后果**：同一件事在不同文档里数字不一致，被追问时无法自证
- **规避**：设立**单一事实源**——数字只从 `eval/baseline_results.json` 出，报告写 `eval_report.md`，其他文档只引用不重算

### 8.3 工程 / 协同坑

**坑 1：embedding 调用无重试**
- **现象**：`embed_text` 一次 SSL 抖动 → 整条 AI 回复失败（消融评测里就有 1 条这样挂掉）
- **后果**：偶发失败被当成"模型问题"，且污染评测结果
- **规避**：加 **3 次重试 + 指数退避（1s/2s）**；同时接受"1 条失败样本如实记入 `failed_count`"而不是悄悄剔掉

**坑 2：正则拦得太宽，把自己的演示路径拦死了**
- **现象**：高危正则一开始把"穿过/污损"也当纠纷关键词拦掉
- **后果**："穿过沾了粉底液能退吗"在进模型前就被拦截转人工——**退款试算 + HITL 确认卡这条最能体现设计水平的路径永远不会被触发**（演示时会显得系统很笨）
- **规避**：**正则范围有意收窄**，只拦投诉/法律/曝光类；"穿过/污损"这类业务判断交给 `calc_refund` 工具做。**拦截规则要按"业务语义"设计，不能按"看起来像纠纷"设计**

**坑 3：为了让 Demo 好看，埋了个会误导模型的暗兜底**
- **现象**：`query_order` 在用户没给单号时，代码 `found = orders[0]` 偷偷返回第一条订单
- **后果**：演示效果好，但与"模型自主决策"目标冲突——**模型会学成永远不传 `order_id`**，真实场景直接回答错误订单
- **规避**：改为显式开关 `fallback_to_first`（默认关），未命中返回 `need_order_id=True` 由模型追问。**凡是"代码替模型做决定"的兜底，都要问一句：它会不会教坏模型**

**坑 4：文档漂移——改了代码不改文档**
- **现象**：① 项目已补 11 张一手截图，`面试深挖补完篇` §0.1 仍写"一张图片都没有"；② 系统已从"意图硬路由"改成 function calling，多份文档仍描述旧流程；③ `prototype/` 只有 7 页，外部一直说"25 页原型"
- **后果**：自己人被过期文档误导，面试口径前后不一
- **规避**：**改代码必须顺手更新"单一事实源"文档**；本册 + `功能全景-给协作方.md` 就是为此设立的对照基准

## 附录 C：面试高频深挖题（8 问）

### Q1：你的项目跟别的 AI 客服作品集有什么不一样？
> 大部分是"上传 PDF → 问答"的 RAG 套壳。我的不同在于：① 做了 8 家竞品拆解，发现"跨平台中立售后"这个结构性空白，不是为了做 RAG 而做 RAG；② 定义了完整指标体系并写死口径（防行业"口径游戏"）；③ 有 5 家店铺 11 张一手实测 + **67 题分层评测 + 消融对照**，不是纸面设计。

### Q2：RAG 到底给你的产品带来了什么？（**核心题**）
> 我做了消融对照才敢回答——**RAG 的价值不在"答得更准"**：常规售后问答 94.6% vs 92.9%，没有显著提升（题目偏常规、模型凭常识就能答，`normal` 桶甚至掉了 3 题，说明塞原文反而干扰）。它不可替代的是**人机分流**：该转人工的判断从裸模型 **0% 提升到 90.9%**——裸模型压根没有"该不该转人工"这个概念，11 道超范围题它全答了。**我据此把优化重点放在分流准确率和超范围问题的可控处理上，而不是盲目堆检索。**

### Q3：你的评测本身可靠吗？（**追问陷阱，答好加分最多**）
> 不可靠，我标了四条局限：判定用的是**关键词命中率代理指标**不是人工评分；RAG 那一臂走的是**传统检索链路、没走新的 Agent 全链路**；**embedding 成本没计入**；67 题样本偏小。
> 而且我发现这套指标**会奖励幻觉**——有一题问"面料是什么"，裸模型编了个"棉质面料"命中关键词判对，我的系统如实说"没资料"转人工反而判错。**越诚实得分越低**，所以我才推翻旧口径、把判定对象换成真实生成的回答，并补了 baseline 臂做归因。

### Q4：Agent 跟 ChatGPT 有什么区别？你怎么保证它不乱来？
> 区别在**它动手，不只是动嘴**——我不把分支写死在代码里，而是把「查政策/查订单/退款试算/转人工」四个工具的说明书交给模型，让它自己决定调哪个、要不要追问、要不要转人工。加新能力只需补一份工具说明，不动主流程。
> **但安全判断我不交给模型**：① 系统里**根本不存在"执行退款"的工具**，它物理上调不到会打款的函数，只能试算；② 工具一旦返回"需要人工"，**代码立刻中断循环**，不追加一轮问它"你接下来想说什么"；③ 投诉/法律类高危词在**进模型之前**被正则拦掉，0 次 LLM 调用。
> 一句话：**决策可以交给模型，红线必须留在代码里。** 我实测过——只在提示词里写"超范围请礼貌说明"，模型会用嘴拒绝但**不调工具**；必须堵掉"用嘴拒绝"这条退路，它才会正确调用。

### Q5：为什么把原来的意图分类架构推翻了？
> 三个原因：① 原来每轮固定 2 次 LLM（先分类、再生成），成本和延迟翻倍；② 决定权在代码不在模型——模型能理解语言，却被限制成"只能输出一个分类标签"，**每加一个能力就要多写一个分支**；③ 实测出稳定性问题：`traces.jsonl` 里同一句"发什么快递"，两次会话一次判成查订单、一次判成查政策，**同一输入两个结果**，根因是分类环节有两套逻辑打架。所以把决定权交回模型，代码只留执行和安全。

### Q6：0.6 这个阈值怎么定的？
> 不是拍的，是用 67 题在候选阈值上扫出来的。**优化目标不是"回答准确率最高"，而是"转人工判断"——宁可略增误转，也要压住漏转**，因为漏转在售后场景就是客诉风险。定完写进配置默认值。不过我从不把它当行业常数讲，它只是我这套评测集上的一个工作点。

### Q7：店小蜜都免费了，你这项目是不是伪需求？
> 免费的代价是**绑死生态 + 不中立 + 数据不归你**。三家平台全部只服务自家，**没有一家跨平台**，而多平台开店是中小商家常态——这个空白巨头不会填，**帮竞品平台做客服等于自杀**，这是结构性约束不是能力问题。另外它的重心在售前转化（会主动劝买家不退货），售后是附带，客诉场景买家不信任。所以它们的免费战恰好验证了市场价值，也恰好把"跨平台、中立、可溯源"空了出来。

### Q8：这个项目上线了吗？有多少商家在用？
> 没有，这是我个人作品集的 Demo，**没有服务过真实付费商家**——这点我在 README 里写得很明确。所有评测数字都是 67 题评测集（合成 golden set）口径，不等于线上解决率。真实 query 分布要上线后回流，这是我知道的"数据飞轮"下一步。
> 至于技术成熟度：多租户、PII、反幻觉设计原则都写了，但**工程上还是演示级**——`company_id` 在 URL 上不是密钥、没有脱敏中间件、没有留存清理。我知道差距在哪，也知道补的顺序。
