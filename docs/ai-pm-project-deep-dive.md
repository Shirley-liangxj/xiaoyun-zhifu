# 小云智服：AI 产品经理深度解读

> 分析口径：2026-10-15 基于仓库实际代码、Git 迭代历史、`assets/evidence/` 原始实测截图和公开官方资料完成；刻意未读取项目 `docs/` 目录中的既有文档，避免被原有叙事带偏。  
> 事实边界：本文能判断“项目做了什么、代码支持什么、证据证明了什么”，不能仅凭仓库判断“其中哪些工作由你本人独立完成”。涉及个人贡献的表述均标注了使用条件。

## 一句话结论

这不是一个靠“接入大模型 + RAG”取胜的普通客服 Demo，而是一个围绕**售后场景错误成本**设计的“AI 自动处理 + 人工兜底”协同工作台：让 AI 处理有明确知识和低风险的咨询，让不确定、投诉和退款类任务带着上下文进入人工队列，并把失败问题回流成知识库与评测集。

最应该讲的产品判断不是“AI 能回答多少”，而是：

> **AI 客服的价值不是尽可能多答，而是在不牺牲用户信任的前提下，提高可被安全解决的会话占比。**

从作品集标准看，这是一个**产品闭环较完整、技术机制可信、商业与线上证据仍不足的 0→1 AI 产品原型**。可以用于 AI 产品经理面试，但必须如实称为“演示/验证项目”，不能说成已经生产落地、真实降本或真实自动退款。

## 1. 用户问题：不是“客服慢”，而是“自动化没有把问题解决掉”

### 1.1 原始证据揭示了什么

仓库保留了 5 家店铺、11 张客服实测截图。它们显示的不是单一痛点，而是三类连续失败：

1. **理解失败**：用户问“怎么退货”，机器人答非所问、重新问候，或连续发送多条碎片化话术。
2. **流程失败**：用户被迫先选订单/商品；没有有效订单时卡住；菜单里甚至没有退货入口。
3. **协同失败**：机器人答错后无法顺畅转人工，或直接把大量本可自动回答的问题甩给人工，用户需要重新描述。

这些证据支持一个比“客服效率低”更准确的问题定义：

> 中小服饰电商的售后咨询高度重复，但规则例外多、订单状态强相关、退款动作风险高。纯菜单机器人解决率低；纯生成式 AI 又容易编造政策或越权承诺。买家在机器人和人工之间反复切换，坐席仍要从头理解问题。

### 1.2 两类核心用户

| 用户 | 真实任务 | 当前损失 | 项目提供的价值 |
|---|---|---|---|
| 买家 | 快速知道“能不能退、怎么退、订单到哪、退款多少” | 重复描述、被迫选单、答非所问、转人工失败 | 自然语言问答、政策来源、订单查询、明确转人工状态 |
| 客服坐席/店铺运营 | 快速识别高风险问题并正确回复 | 查政策、查订单、重复打字、接管时缺上下文 | 待人工队列、AI 草稿、来源与置信度、快捷话术、知识缺口回流 |

### 1.3 为什么聚焦“服饰售后”是正确取舍

服饰售后同时具备三个适合 AI 产品验证的条件：

- 高频：尺码、物流、退换货、退款时效重复出现；
- 有规则：大部分答案来自店铺政策和订单状态，可被检索和验证；
- 有风险分层：普通政策可自动答，投诉、穿着后退货、退款执行必须人工介入。

因此它比“万能企业客服”更容易定义边界、设计工具和建立评测集。项目范围收得对，面试时不要反过来把它讲成通用客服平台。

## 2. 产品目标与取舍：优化“安全解决率”，不是“自动回复率”

### 2.1 更合适的目标树

**北极星指标：可被安全解决的会话占比。**

它需要同时满足“问题得到解决”和“没有错误自动化”。建议拆成：

- AI 自动解决率：问题由 AI 完成，用户未重复追问、未转人工；
- 转人工判断准确率：该转的转、不该转的不乱转；
- 高风险误执行率：退款、取消订单等动作错误执行，目标必须接近 0；
- 坐席接管效率：从进入队列到首响的时间、平均处理时长；
- AI 建议采纳/编辑率：坐席直接采纳、编辑后采纳、拒绝分别统计；
- 知识缺口闭环率：高频缺口从发现到补库后，相关失败是否下降；
- 用户体验：一次解决率、重复咨询率、CSAT/CX。

当前 Dashboard 的 `ai_accept_rate` 实际按 `ai_suggestion.is_sent` 计算，会混入直接发给买家的 AI 消息，不等同于“坐席采纳率”。所以它可以作为演示指标，但还不能用于真实产品决策。[统计实现](D:/xiaoyun/backend/app/routers/stats.py:50)

### 2.2 项目中已经做出的关键取舍

#### 取舍 A：覆盖率 vs. 正确性

项目没有让模型对所有问题强答。政策检索低于阈值、没有资料、超出领域或大模型调用失败时，会进入人工队列。这个策略牺牲一部分自动化率，换取更低的错误承诺风险。[低置信中断](D:/xiaoyun/backend/app/agent/agent_loop.py:406)

#### 取舍 B：Agent 自主性 vs. 业务安全

工具注册表只有 `calc_refund`（退款试算），没有“执行退款”工具；任何退款试算都会返回 `needs_human=True`，代码立即中断模型循环，生成待确认卡，最后仍由坐席处理。[工具注册表](D:/xiaoyun/backend/app/agent/tool_registry.py:51) [HITL 分支](D:/xiaoyun/backend/app/agent/agent_loop.py:443)

这是一个成熟的产品判断。OpenAI 的 Agent 指南也把取消订单、授权大额退款和付款列为需要人工监督的高风险动作；Gorgias 的生产方案虽然可以真的修改 Shopify 订单，但同样通过动作条件和客户确认控制风险。[OpenAI Agent 指南](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) [Gorgias 动作与确认](https://helpcenter.gorgias.com/en-US/create-an-action-to-connect-ai-agent-to-other-apps-567325)

#### 取舍 C：技术炫技 vs. 可维护性

系统用一个 Agent 加 4 个差异明确的工具，并设置最多 4 轮工具调用，没有过早拆成多 Agent。对当前复杂度这是合理的；复杂度主要来自业务边界，不来自 Agent 数量。[循环上限](D:/xiaoyun/backend/app/agent/agent_loop.py:35)

#### 取舍 D：演示完整性 vs. 生产真实性

为了演示完整任务，项目使用 3 条 mock 订单、演示退款规则和本地 JSON 确认单。这能证明交互和控制逻辑，但不能证明真实订单系统集成、鉴权、并发或资金安全。面试必须主动说明，不要等面试官追问。[演示订单](D:/xiaoyun/backend/app/data/orders_demo.json) [退款默认值](D:/xiaoyun/backend/app/agent/tools/refund_calc.py:33)

#### 取舍 E：过程透明 vs. 买家认知负担

买家端展示“执行计划”、来源和演示标记，对作品集答辩很好，因为能看见 Agent 在做什么；真实产品中，内部工具名和完整计划未必应该暴露给买家，更适合转成“正在查询订单 / 正在核对政策 / 需人工确认”这样的任务状态。[买家计划卡](D:/xiaoyun/frontend/src/pages/Chat.jsx:19)

## 3. 系统与技术机制：技术是产品边界的执行方式

### 3.1 系统分层

```text
买家聊天页 / 坐席工作台
          ↓
FastAPI 会话与权限层
          ↓
风险前置拦截 → 单 Agent function calling 循环（最多 4 轮）
          ↓
政策检索 | 订单查询 | 退款试算 | 转人工
          ↓
SQLite 会话/知识缺口 + FAISS 租户索引 + JSONL 运行轨迹
```

### 3.2 六个关键机制

1. **领域约束与工具选择**：系统提示词限定服饰售后；模型按问题选择政策检索、订单查询、退款试算或转人工，而不是先做固定四分类。[Agent 指令](D:/xiaoyun/backend/app/agent/agent_loop.py:37)
2. **代码级硬护栏**：投诉、法律、曝光等关键词在调用模型前拦截；命中时 LLM 调用数为 0。工具只要返回 `needs_human=True`，循环立即停止，模型不能靠下一句话绕过。[风险拦截](D:/xiaoyun/backend/app/agent/intent_router.py:22)
3. **RAG 知识回答**：知识文档按 400 字、50 字重叠切块，用 `embedding-3` 向量化，按公司维护独立 FAISS 索引，再由 GLM-4-Flash 生成回答。[RAG 切块](D:/xiaoyun/backend/app/services/rag.py:11) [租户索引](D:/xiaoyun/backend/app/services/vector_store.py:29)
4. **来源与“置信度”**：前端展示命中文档；系统把 top-3 向量相似度平均后线性映射为 0.4–0.95，再与阈值比较。[置信度公式](D:/xiaoyun/backend/app/services/ai_suggestion.py:45)
5. **人机协同**：低置信/高风险会话进入 `waiting_human`，坐席可接入、查看上下文与 AI 建议、直接采纳/编辑/拒绝，并可转工单。[坐席接管](D:/xiaoyun/backend/app/routers/conversations.py:294) [建议采纳](D:/xiaoyun/backend/app/routers/conversations.py:213)
6. **持续改进**：低置信问题累计为知识缺口；运营补充标准答案后可生成知识文档并重建索引；同时每轮 Agent 轨迹以 JSONL 留存，支持 bad case 回放。[知识缺口](D:/xiaoyun/backend/app/services/knowledge_gap.py:9) [轨迹记录](D:/xiaoyun/backend/app/agent/trajectory.py)

### 3.3 需要准确解释的技术边界

- 当前所谓“置信度”不是经过标注数据校准的成功概率，只是检索相似度的启发式映射。面试应称“检索置信分”或“路由分数”，不要说“模型有 80% 把握”。
- 高危正则是便宜且确定的第一道护栏，但会漏掉同义表达，也可能误伤包含“投诉”等词的正常咨询；它不是完整安全分类器。
- 订单查询没有真实买家身份校验，因为当前只是 mock 数据。接真实电商平台前必须验证订单归属、权限、幂等、操作日志和撤销/补偿机制。
- 旧版 `pending_confirmations.json` 适合单机 Demo，不适合多实例生产环境；当前已迁移为 `human_review_actions`，但仍缺过期策略与并发锁。
- 退款试算在金额/天数缺失时默认使用 199 元和第 5 天，这对演示方便，但从产品安全看应该改为追问或从已验证订单读取，绝不能带入生产。[默认值](D:/xiaoyun/backend/app/agent/tools/refund_calc.py:33)

## 4. 一笔完整任务：从“我要退款”到人工接管

下面选一条最能体现产品判断的任务，而不是挑最简单的 FAQ：

> 买家：“订单 DEMO-1002，签收第 5 天，针织开衫没穿过，想退款。”

### 4.1 代码设计的完整路径

1. 买家消息进入 `/api/public/chat`，系统创建或复用会话并保存原话。
2. 高危规则未命中，进入 function calling 循环。
3. 模型先调用 `query_order(DEMO-1002)`；工具返回商品、268 元、已签收、第 5 天等演示数据。
4. 模型读取工具结果，再调用 `calc_refund(order_id=DEMO-1002, amount=268, days_since_purchase=5)`。
5. 规则计算“7 天内、未声明穿着”，给出 268 元试算；但工具同时返回 `needs_human=True` 和 `auto_execute=False`。
6. Agent 循环被代码硬中断，不再让模型自由发挥；买家端出现“建议退款 ¥268、不会自动打款”的确认卡。
7. 买家点击“确认提交给人工”，确认单状态更新，会话进入 `waiting_human`。
8. 坐席工作台把待人工会话置顶，坐席看到买家原话、订单/试算上下文和 AI 建议，接入后完成真实审核与回复。
9. 系统记录调用过的工具、是否转人工、LLM 调用次数和中断原因，供后续回放。

### 4.2 这条任务为什么适合面试

它一次性说明了五件事：

- 模型负责理解与编排，不直接掌握资金权限；
- 结构化订单数据与知识库资料职责不同；
- 规则引擎处理金额和时间，避免纯文本模型心算与编造；
- 用户确认不等于机器执行，真正高风险动作仍交给人；
- 失败与接管不是系统异常，而是产品流程的一部分。

### 4.3 尚未被实测证明的部分

上述路径是代码支持的预期路径，但本次没有调用真实 GLM API 做端到端验证，因此不能断言模型每次都会按“查订单 → 试算 → 确认”正确选工具。当前自动化测试只验证了 40 题题库结构，没有覆盖这条多轮工具链。

## 5. 质量证据：目前证明了什么，还没有证明什么

### 5.1 已有证据

#### A. 一手竞品/现状观察

11 张实测截图证明了真实体验缺口：菜单覆盖不足、自然语言理解不稳、流程依赖选单、转人工不连续。这是“为什么做”的证据，不是“做完有效”的证据。

#### B. 历史 67 题消融对照

仓库保留了两次同题双臂结果：

| 运行 | 裸模型整体准确率 | RAG 整体准确率 | 裸模型转人工准确率 | RAG 转人工准确率 | RAG 应答准确率变化 |
|---|---:|---:|---:|---:|---:|
| Run 1 | 82.09% | 89.55% | 0% | 81.82% | -7.14pp |
| Run 2 | 79.10% | 92.54% | 0% | 90.91% | -1.78pp |

来源：[Run 1](D:/xiaoyun/eval/baseline_results_run1.json:8) [Run 2](D:/xiaoyun/eval/baseline_results.json:8)

最重要的结论不是“RAG 让回答更准”。事实上，两次运行里的应答准确率都下降了。RAG 的主要贡献是让系统拥有**拒答/转人工边界**，从而把整体准确率拉高。这反而是更有价值的 AI PM 洞察：

> 在高风险客服场景，RAG 的产品价值可能首先体现在“知道何时不该答”，而不是让每个答案听起来更聪明。

同时，RAG 平均 token 从约 177 增到约 689，约为 3.9 倍；P50 延迟变化不大。这说明项目已经开始比较质量、成本和延迟，而不是只报单一准确率。

#### C. 当前 40 题回归集的结构测试

当前题库包含 35 道应答题、5 道安全转人工题。结构测试验证题目数量、连续 ID、转人工样本数和应答题关键词锚点；本次实际运行 3 项测试，均通过。[结构测试](D:/xiaoyun/backend/tests/test_eval_questions.py:17)

### 5.2 现有评测的关键漏洞

当前页面上的“回答准确率”并没有评判模型最终回答。评测代码只检索知识块，并检查**被检索文本**是否覆盖至少一半关键词；它没有调用 Agent，也没有检查最终回复、工具选择、参数和多轮完成情况。[关键词判定](D:/xiaoyun/backend/app/services/eval_runner.py:39) [检索文本检查](D:/xiaoyun/backend/app/services/eval_runner.py:124)

因此现阶段不能证明：

- 40 题当前版本的真实准确率；
- Agent 是否选对工具、传对订单号和金额；
- 回答是否忠于来源、有没有编造或遗漏关键例外；
- 多轮任务是否最终完成，人工是否真的接上；
- 真实用户的一次解决率、满意度和坐席节省时间；
- 阈值 0.6 是否为成本最优点。

### 5.3 下一版评测应怎样补

#### 离线评测

1. **路由**：工具选择准确率、该追问时是否追问、该转人工时是否转。
2. **参数**：订单号、金额、天数、商品状态的抽取准确率。
3. **回答**：事实正确性、来源忠实度、政策例外覆盖、禁用承诺检查。
4. **任务**：多轮成功率、平均工具轮数、失败中断原因。
5. **安全**：高风险误执行率、确认前执行率、跨用户订单访问率。
6. **工程**：P50/P95 延迟、token/单、接口失败率、人工接管成功率。

#### 在线/试点指标

- AI involvement rate 与 verified resolution rate；
- 误转人工率、漏转人工率；
- 用户重复追问率、转人工后重复描述率；
- 坐席首响时间、平均处理时长；
- AI 建议直接采纳率、编辑后采纳率、拒绝率；
- 知识缺口补齐前后的相关问题解决率；
- CSAT/CX 与投诉率。

成熟厂商也把测试、会话级结果和持续改进作为一套系统：Intercom 支持批量模拟、答案检查和来源可解释，并从失败会话与人工回复中生成按影响排序的知识缺口建议；Zendesk 支持流程版本、发布前测试、会话日志以及自动解决/辅助升级/未解决等结果状态。[Intercom 测试与答案检查](https://www.intercom.com/help/en/articles/7120684-fin-ai-agent-explained) [Intercom 知识缺口](https://www.intercom.com/help/en/articles/11394959-use-ai-powered-content-recommendations-to-improve-fin) [Zendesk 流程测试](https://support.zendesk.com/hc/en-us/articles/10040865503898-Managing-generative-procedures-for-AI-agents) [Zendesk 会话日志](https://support.zendesk.com/hc/en-us/articles/8357749580186-Reviewing-conversation-logs-for-AI-agents)

## 6. 与行业成熟方案相比：项目处在什么位置

| 维度 | 小云智服现状 | 成熟方案常见做法 | 判断 |
|---|---|---|---|
| 知识回答 | 本地文档、FAISS、来源展示 | 多知识源同步、受众隔离、答案检查 | 已有骨架，缺内容治理 |
| 业务动作 | mock 查单、退款试算 | 接 Shopify/CRM/物流，取消、改址、退货、补发 | 最大生产差距 |
| 风险控制 | 正则、低置信转人工、HITL、最大轮数 | 动作条件、客户确认、鉴权、操作审计、补偿机制 | 产品方向正确，工程深度不足 |
| 人工协同 | 待人工队列、建议采纳/编辑、工单 | 全渠道路由、SLA、技能组、完整客户记录 | 完成核心演示闭环 |
| 可观测性 | JSONL 轨迹、来源、简单看板 | 会话状态、动作/API 日志、QA、主题趋势 | 可用但不够运营化 |
| 持续改进 | 低置信问题累计、手工补库 | 失败会话聚类、对照人工回复、缺口排序、冲突检测 | 是亮点，优先继续做深 |
| 质量评测 | 检索关键词与历史消融 | 场景模拟、端到端任务评测、发布门禁、线上结果 | 当前最需要补强 |

Gorgias 已能根据订单状态执行取消、改地址、移除/替换商品和补发，并明确列出 3PL 同步、税费变化、多商品替换等限制。这说明行业竞争已从“能回答”进入“能在条件与权限控制下完成任务”。[Gorgias Shopify Actions](https://helpcenter.gorgias.com/en-US/ai-agent-actions-make-changes-to-shopify-orders-757792)

所以这个项目最合适的定位不是“对标成熟 AI 客服平台”，而是：

> **用一个可运行的缩小版系统，验证中小服饰电商售后中“知识回答—业务工具—风险护栏—人工接管—失败回流”的产品闭环。**

## 7. 个人贡献与迭代决策：怎样讲才真实又有分量

### 7.1 仓库能证明的项目级迭代

Git 历史显示出一条清晰演进：

1. 先做买家问答、坐席工作台、知识库和 AI 建议；
2. 再从普通 RAG 升级到 function calling，增加政策检索和转人工工具；
3. 针对“发什么快递被误判成查订单”等 bad case 修正规则；
4. 增加高危前置拦截、退款 HITL、轨迹记录和最大轮数兜底；
5. 增加 67 题消融评测，发现裸模型几乎不会正确转人工；
6. 再把 67 题探索集收敛为 40 题、每题有判断锚点的回归集。

这条链路适合讲成“问题驱动的迭代”，而不是按页面罗列功能。

### 7.2 不能直接下结论的部分

仓库不能证明这些提交、调研、产品设计、代码或评测是否全部由你独立完成。面试前必须补一张“贡献边界表”：

| 模块 | 你是否主导 | 你具体做了什么 | 谁协作 | 可出示证据 |
|---|---|---|---|---|
| 用户调研 | 待补 | 样本选择、问题设计、截图归纳？ |  |  |
| 产品定义 | 待补 | 用户、范围、成功指标、优先级？ |  |  |
| 交互原型 | 待补 | 买家端/坐席端/HITL 流程？ |  |  |
| AI 机制 | 待补 | RAG、工具、阈值、护栏的方案还是编码？ |  |  |
| 评测 | 待补 | 题库、判定标准、消融、结论？ |  |  |
| 开发交付 | 待补 | 独立开发、AI 辅助开发还是与工程协作？ |  |  |

只有确认真实后，才能把“项目做了”改写成“我主导/我设计/我推动”。

### 7.3 可直接使用的 3 分钟讲法（需按真实贡献替换主语）

> 我做的是一个面向中小服饰电商的 AI 售后协同工作台。起点不是想做一个聊天机器人，而是我实测了 5 家店铺的售后客服，发现用户真正的问题是机器人经常答非所问、强制选订单，而且一旦答错很难连续地转人工。  
>  
> 因此我把目标定成“提高可被安全解决的会话占比”，而不是单纯提高自动回复率。产品上同时服务买家和坐席：低风险政策问题由 AI 基于知识库回答；订单问题调用查询工具；退款只做规则试算，不直接打款；低置信、投诉或超出范围的问题带着上下文进入人工队列。  
>  
> 系统采用单 Agent 加 4 个工具。关键安全判断不只写在提示词里：高危问题会在调用模型前拦截，工具一旦返回需要人工，代码就立即中断；退款还必须经过用户确认，再交给坐席。这样把“模型会不会听话”变成可执行的产品边界。  
>  
> 一笔完整任务里，用户提供订单号并申请退款，Agent 先查订单，再按金额和签收天数试算，展示不会自动打款的确认卡；用户确认后进入人工队列，坐席看到上下文和 AI 建议后完成审核。  
>  
> 质量上我没有只看 Demo 效果，而是做了同题消融。两次 67 题结果显示，RAG 并没有提升应答题准确率，反而小幅下降，但把转人工准确率从 0 提升到约 82%–91%。这让我把产品价值从“回答更聪明”调整为“边界更可靠”。当前不足是评测还没有覆盖完整 Agent 工具链，也没有真实商家线上指标；下一步会先补端到端评测和真实订单只读接入，再决定是否扩大自动动作范围。

注意：如果用户调研、评测或技术方案并非你本人主导，要把对应的“我做了”改成“项目中我们做了，我具体负责……”。

## 8. “解读到什么程度合适”的明确答案

### 8.1 简历：讲到产品判断和结果，不讲实现细枝末节

简历只需要 1 句定位 + 2–3 条贡献：

- 为什么选这个问题，服务谁；
- 做了哪项关键机制与取舍；
- 用什么证据验证，结果和限制是什么。

不要在简历堆 `FastAPI / React / FAISS / GLM`。技术名只保留到能说明产品机制的程度，例如“基于 RAG + function calling 构建政策检索、订单查询、退款试算与转人工工具链”。

### 8.2 作品集：正好按本文六段叙事

1. 用户问题；
2. 产品目标与取舍；
3. 系统与技术机制；
4. 一笔完整任务；
5. 质量证据；
6. 个人贡献与迭代决策。

每一段都要回答“为什么这么做”，不能只截页面、贴架构图。

### 8.3 面试：准备三层深度

- **30 秒**：一句定位 + 用户痛点 + 核心差异；
- **3–5 分钟**：完整叙事，重点讲取舍和一笔任务；
- **15–20 分钟追问**：阈值怎么定、为什么单 Agent、如何防误退款、评测为什么这样设计、下一步怎样接真实订单。

AI 产品经理讲到“能把技术机制翻译成产品边界、能用证据承认失败、能说明下一步决策”为止就够了。无需主动讲 SQLAlchemy 模型、接口文件结构或 React 组件；除非技术面试官追问。

## 9. 最优先补强的 5 件事

1. **补一套端到端 Agent 评测**：覆盖工具选择、参数、多轮任务、最终回答和转人工，而不是只测检索文本。
2. **修正指标语义**：把“AI 建议采纳率”拆成自动发送、坐席直接采纳、编辑后采纳、拒绝；把“置信度”改名为检索路由分。
3. **消除危险默认值**：金额和签收天数缺失时必须追问或查订单，不能默认 199 元/5 天。
4. **做真实系统的只读接入**：先验证订单归属、状态和物流，不急着开放真实退款；先读后写是合理的渐进路线。
5. **做一个小规模试点**：即使只有 1 家店、2 周、100 条匿名会话，也比继续加页面更有价值。重点记录一次解决率、人工接管成功率、重复描述率和坐席处理时长。

如果只能做一件事，优先做第 1 件。它会把项目从“看起来完整”推进到“质量可被复核”，也是当前与成熟 AI 产品差距最大的地方。
